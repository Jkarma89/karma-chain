## 一、既有事实基线（全部为实测，不是推断）

### 范围 A 的成因链

| # | 环节 | 证据 |
|---|---|---|
| 1 | 两个 Primary 停 → 五个 L1 自报综合健康位 `/ext/health` 全部 **503** | 逐台直连实测（2026-09-10） |
| 2 | 代理容器的 Docker healthcheck 是 `wget -q -O - http://127.0.0.1:<port>/ext/health` | `docker/compose/lan-*.yml`、`local-local.yml` 六份；由 `render-compose.mjs` 生成 |
| 3 | 该请求**经由代理自己**打到上游 —— nginx 访问日志里 User-Agent 为 `Wget`、client 为 `127.0.0.1` | 代理容器日志 |
| 4 | `proxy_next_upstream error timeout http_502 http_503 http_504` 把上游的 **503 应答计为一次失败** | `blockchain/nodes/lan/rpc-proxy.conf` |
| 5 | `max_fails=1 fail_timeout=60s` —— **一次**失败关该上游 60 秒 | 同上 |
| 6 | `proxy_next_upstream_tries 5` 让**同一个** healthcheck 请求依次试完五个上游 → **一次毒遍全部** | 日志里一条请求连续四行 `upstream server temporarily disabled` |
| 7 | healthcheck 间隔 **10 秒 < 60 秒**惩罚期 → 惩罚期永不排空 | compose 的 `interval: 10s` |
| 8 | 真实客户端流量随之 `no live upstreams` → **502** | 日志里 `POST /ext/bc/karmachain/rpc … 502`，以及 `POST … 200` 的偶发漏过窗口 |

### 一个此前没被注意到的放大器：`zone`

`upstream` 块里有 `zone karmachain_rpc 64k;`，它让 `max_fails` / `fail_timeout` 的状态
**在所有 worker 之间共享**。生成器注释记着 002 的实测：`nginx:alpine` 默认
`worker_processes auto`，本机起了 **18 个 worker**。

`zone` 本身是 002 为**另一个**问题加的正确修复（不加它，失败计数每个 worker 各记一份，
整域缺席时几乎每次请求都命中一个"还不知道那台已死"的 worker，重新付 2 秒连接超时）。

但它同时把本缺陷从"每个 worker 各自被毒"放大成**一次探测毒遍全体 worker 的共享状态**。
**一个正确的修复放大了另一个缺陷** —— 这条值得记下来，因为它说明
"每个改动单独都对"不等于"合起来也对"。

### 范围 B 的判据

| # | 事实 | 证据 |
|---|---|---|
| 1 | 两个 Primary 全停时，L1 **照常出块** | 直连 l1-1 的交易确认于区块 835、4108 ms |
| 2 | 同一时刻面板报 `normal / 100%`，**这是对的** | 五份快照一致 |
| 3 | 但此时 `restart` 一个 L1 验证者，它**再也回不来** | l1-1 重启后 5 分钟 P 链 `isBootstrapped` 恒 `false`；L1 那条链在该节点上根本没被创建 |
| 4 | 原因是**连上的 P 链权益**不够，不是拿不到数据 | `percentConnected: 0` / `"required at least 80.000000%"`；同时 `connectedPeers: 4`（其余四个 L1 都连上了） |
| 5 | **一个 Primary 不够** —— 各握 50%，门槛 80% | 起回 primary-1 后仍卡住，自报 `percentConnected: 0.5` |
| 6 | 两个都齐了 → **约 36 秒**自愈，无人工干预 | P 链引导 → L1 链创建并引导 → 高度对齐 → 面板回 `normal/100%` |
| 7 | 停摆与卡住**不损坏任何东西** | 链停期间那笔 45 秒无回执的交易，恢复后被**原样打包进区块 834** |

全部细节见 [003 的 research.md V-07 / V-08](../003-chain-health-dashboard/research.md)。

## 二、决策

### R-01 · 代理的 healthcheck 改成**完全不碰上游**的自检

**决策**：在生成的 nginx 配置里加一个专用位置（形如 `location = /_alive`），
由 nginx 自己直接应答，**不 `proxy_pass`**；Docker healthcheck 改为 GET 这个位置。

**理由**：

1. 它**彻底切断病因**。缺陷的机制是"健康探测制造上游失败"。
   探测不再接触上游，就没有任何东西在制造失败 —— 真实 RPC 流量拿到的是 200，
   200 不会被计为失败，惩罚期永远是空的。
2. 它是**最小改动**：生成器加几行、compose 那一行换个路径。
   不动 `proxy_next_upstream`、不动 `max_fails`、不动 `fail_timeout`（见 R-02）。
3. 它回答的问题**恰好是容器健康位该回答的那个** —— "这个容器本身有没有在正常工作"：
   nginx 进程活着、配置解析通过、端口在监听。
   "链能不能通过它用起来"是另一个层级的问题，已经有两处在管（见 R-03）。
4. 它**不需要** busybox `wget` 支持 POST（见 R-04 被否方案）。

**代价 / 需要交代的一点**：这个判据**不覆盖**「改写与转发是否正确」。
规格 FR-002 的第二个分句字面上要求覆盖它。处理见 R-03 —— 并在 plan 里作为
**一条需要确认的规格措辞问题**列出，不静悄悄地把 FR 缩小。

**曾考虑并否掉的方案**：

| 方案 | 否掉的理由 |
|---|---|
| **POST `eth_chainId` 经 RPC 路径**（覆盖改写+转发） | ① 仍然接触上游，只是把"必然制造失败"换成"可能参与制造失败"；② **会引入一种新的假红**：所有 L1 引导中时该路径返回 404（链还没注册），healthcheck 变红，而代理完全正常 —— 引导常常超过 `start_period: 60s`；③ 依赖 busybox `wget --post-data`，未验证 |
| **删掉 `proxy_next_upstream` 里的 `http_503`** | 这会改变**真实流量**的故障转移语义（一个 502/503 不再换下一个上游），为了修探测的问题去动业务路径，方向错了 |
| **把 healthcheck 间隔拉长到 > `fail_timeout`** | 只是把中毒频率降低，病因没去掉；而且会让容器健康位的延迟变差 |
| **直接删掉代理的 healthcheck** | 那就再也不知道代理死了。**一个不会变红的守卫比没有守卫更坏，而没有守卫也是坏的** |
| **改用 nginx 的 `stub_status`** | 需要额外的 `--with-http_stub_status_module`（`nginx:alpine` 自带，但它暴露连接计数等信息，且语义仍是"nginx 活着"），比 `return 200` 复杂而不更强 |

### R-02 · **不动** `max_fails` / `fail_timeout` / `proxy_next_upstream`

**决策**：三者一律保持原值。

**理由**：它们是 002 在 **2026-09-09 实测后专门定下**的，生成器里写着完整推导：

- `max_fails=2 fail_timeout=10s` → `max_fails=1`：原值在**低频请求下等于没生效**
  （请求间隔一旦超过 `fail_timeout`，窗口内只累积到 1 次失败，永远到不了 2 次，
  死节点因此从不被标记，每个请求都要重新付连接超时。5 次测量 5 次都付了）。
- `fail_timeout` 15s → 60s：**反复去探一个持续死着的后端没有收益**；
  而 `ip_hash` 在后端被标记/恢复时会重新分配，每分钟 4 次重探 = 每分钟 4 次机会打断
  "读到自己刚写的"那份亲和性。注释里明确写了这**不是一个已确认的修复**，
  但"这个值本身站得住，与那次故障无关也该改"。

**当前的 502 不是这些参数的错。** 病因是探测在制造失败。
**先去病因，再谈剂量** —— 去掉病因之后如果仍有可观测的问题，那时再带着新的实测来调。

这满足 FR-006 对"若决定不改动，同样必须记录为何无需改动"的要求。

> **这条是本期最容易做错的地方。** 看到 `max_fails=1 fail_timeout=60s` 会本能地觉得
> "太激进了，放宽一点"。但那是一份**有实测支撑的决定**，而且放宽它会把 002 已经解决的
> 另一个问题放回来。改一个自己没有量过的参数，是在用别人量过的结论换自己的直觉。

### R-03 · 「改写与转发是否正确」由谁保证 —— ✅ **已拍板（2026-09-11）**

**决策**：不由容器健康位保证，而由既有的三层保证。
**已按倾向 (a) 落地为规格改动**：FR-002 只保留「进程 / 配置 / 监听」，
「改写与转发」拆出为 **FR-034**，明确由静态守卫 + 系统级检查覆盖。

1. **静态**：改写规则是生成物的一部分，由 `npm run render:check` 的漂移核对
   与 `tests/unit/rpc-proxy-failover.test.mjs` 守着。它是**静态属性** ——
   运行期健康位每 10 秒重验一次静态属性没有收益。
2. **系统级**：`devnet-verify` 的检查项经代理入口跑。
3. **持续**：003 的面板本来就在持续探代理路径（`pathAlive`），
   并且**按契约不许碰 `/ext/health`**（`tests/unit/dashboard-boundaries.test.mjs` 静态禁止）。

**（已落地，以下保留原始论证）** 原 FR-002 写的是健康判定必须反映
「进程在监听，**且能把面向客户端的 RPC 路径正确改写并转发到上游**」。
按 R-01 的决策，容器健康位只覆盖前半句。两种改法：

- (a) 把 FR-002 的第二个分句移到一条新 FR，明确它由静态守卫 + 系统级检查覆盖；
- (b) 保留 FR-002 原样，改用 R-01 被否掉的 POST 方案 —— 但那要接受"引导中假红"的代价。

**已选 (a)**，理由是 FR-003（探测不得把上游关进惩罚期）与原 FR-002 后半句
在**同一个探测里**天然冲突：要验证转发就必须接触上游，接触上游就可能参与失败计数。
把两件事拆到两个机制里是唯一能同时满足的结构。

**拍板带出了四处连带矛盾**，都已改正：原 **FR-008**、**SC-007**、**US1 场景 4**、
以及边界情形「全部 L1 都不可服务」——它们**全都**要求「全部 L1 不可服务时代理健康位变红」，
而按拆分后的划分，那种情形下代理确实在正常履行职责。
**一处措辞改动牵出四处矛盾，说明原先那句话不是笔误，是一个贯穿全文的错误理解** ——
我写规格时把「代理健康位」和「链可用性」当成了一回事，正是本期要修的那个混淆本身。
现已统一为「nginx 自己死了或配置坏了才变红」，并新增 US1 场景 5 专门覆盖变红。

### R-04 · 恢复能力需要**第三个**谓词，不能复用 `participatesInConsensus`

**决策** ✅ **已拍板（2026-09-11）**：新增一个从同一套状态词汇派生的谓词
（`servesPChain`），**不复用** `participatesInConsensus`。
**已落地为 FR-017 的改写**，并顺带改正了边界情形里同一处措辞
（那是「拿错谓词」这个坑的**第三种**踩法 —— 003 的 data-model §0 记着前两种）。

**理由（这是本期最关键的一处）**：`participatesInConsensus` 的第一行就是

```js
if (!row.countsTowardTolerance) return false;   // Primary 不参与 L1 出块（研究 R-09）
```

Primary 的 `countsTowardTolerance` 恒为 `false`，所以该函数对**任何** Primary
都返回 `false` —— **不论它是活着还是停着**。拿它去数"有几个 Primary 在参与"，
答案恒为 0，于是恢复能力提示会**永远亮着**。

**规格 FR-017 已按此改写**（原文「MUST 与 003 的 `participatesInConsensus` 同源」
字面上不可实现）：现为「MUST 派生自**同一套状态词汇**
（`healthy` / `catching-up` / `bootstrapping` / `starting` / `stalled` / `unreachable`）
与**同一条 `unreachable` 双重含义判据**，且 MUST NOT 复用那个函数本身」。

新谓词的判据（与 `participatesInConsensus` 同形状，但作用于 Primary）：

| `state` | `servesPChain` | 为什么 |
|---|---|---|
| `healthy` | ✅ | 在服务 |
| `catching-up` | ✅ | 在追块但在服务（与 `SERVING_L1` 同理） |
| `bootstrapping` / `starting` | ❌ | 还没在服务 —— 这正是 003 §0 那条教训 |
| `stopped` / `stalled` / `identity-mismatch` / `data-corrupt` | ❌ | 故障 |
| `unreachable` 且 `countsAsOffline === false` | ✅ | 其余节点看得见它 → 它活着，断的是**本机到它的路径**（FR-018） |
| `unreachable` 且 `countsAsOffline === true` | ❌ | 整域缺席 → 它真的不在 |

**这是本仓库里第三个"在线"谓词。** 三个各自回答一个不同的问题，
必须在 data-model 里并排列清，否则下一个人还会拿错一个 ——
003 的 §0 已经为前两个写过一遍，本期是第二次重演同一个形状。

### R-05 · 恢复能力是**正交维度**，不是第六档

**决策**：不进健康档位枚举，作为独立字段 + 一条新的异常分类 `recovery-blocked`。

**理由**：003 的五个状态（`observer-blind` / `starting` / `stopped` / `zero-margin` /
`normal`）是**互斥**的，靠 P1…P5 严格优先级判定。恢复能力与它们全部正交 ——
链可以是「正常出块 + 无法恢复」，也可以是「已停止 + 无法恢复」，
两条信息必须能同时呈现（spec 的边界情形第 5 条）。塞进同一个枚举就会丢掉一半。

`recovery-blocked` 成为第**六**类异常，与既有五类（`observation` / `node-infra` /
`sync-lag` / `consensus-margin` / `chain-identity`）并列，并带自己的处置方向。

**注意它与 `node-infra` 的关系**：两个 Primary 停着时，既有逻辑已经为每个 Primary
产生一条 `node-infra`（"到那台机器上查节点进程"）。新增的 `recovery-blocked`
是**链层面**的一条，说的是那两条合起来的后果。二者并存是对的，不是重复。

### R-06 · 门槛写 `2`，不写 `80%`

**决策**：判据是「`servesPChain` 为真的 Primary 数 < 2」。
**不**把 80% 这个百分比写进任何判据。

**理由**：80% 取自 avalanchego 自己的健康消息，是**它的内部门控参数**，
不在本仓库的事实来源里，也可能随版本变化。而"必须两个都在"是我们能直接观测、
直接断言、也直接告诉人的事实。把百分比写进判据等于引入一个我们控制不了、
也没在 `protocol.json` 里的隐含依赖。

**同时这条也必须写进数据模型的注释里**：`2` 这个数字**恰好**等于当前 Primary 总数，
所以它看起来像"全部都要在"。但它的来源是**权益门槛**，不是"总数"——
如果哪天 Primary 加到 3 个（各 33%），门槛 80% 就需要 3 个全在，而不是 2 个。
把它写成"总数"会在拓扑变化时静悄悄地给出错误结论。**留待那个特性去解决，
本期只把注释写对。**

### R-07 · 对外精简视图零改动

**决策**：不新增任何字段；`public-view.mjs` 的白名单与自检保持原样。

**理由**：恢复能力描述的是这张网**在拓扑层面的脆弱窗口**。
对外暴露只提供攻击时机，而对外部使用者没有任何可操作价值（他们既看不到 Primary
也管不了它）。宪法第四条安全优先。

**这条要有守卫**：断言公开投影的字段集合**与本期开始前逐字段相同**（SC-011）。
不是"不含 recovery 字段"这种否定式断言 —— 那种写法漏掉下一个新增字段。

### R-08 · 两种部署形态同改同验

**决策**：`local` 与 `lan` 两种形态的 compose 与 nginx 配置都由同一处生成器改，
并各自跑一次验证。

**理由**：003 的教训是「在一台机器上验过不等于验过」（win-2 上连撞四次，
其中三项是被 win-1 掩盖的 002 遗留缺陷）。本期的 e2e 跑在 `local` 形态，
真实部署是 `lan` 形态 —— 只改一种会让测试与部署背离，而那正是本期要修的缺陷
当初能活下来的原因。

## 三、待实测项（本期结束前必须闭合）

> 现在写的全部是**决策**。下面每一条都还是推断，标 ❌ 的一个都不许在验收里当成事实。

- **V-01** ❌ `location = /_alive` 的 nginx 配置能被 `nginx -t` 接受，且容器内
  `wget -q -O - http://127.0.0.1:<port>/_alive` 返回 0。
- **V-02** ❌ **变红检查（范围 A）** —— 判据已随 R-03 拍板定下：
  验的**不是**"上游死了它会红"（按设计那时它就该绿），而是
  **"nginx 自己死了或配置坏了它会红"**。两条都要做：
  ① 杀掉 nginx 进程 → 健康位转不健康；
  ② 把配置改坏到无法加载 → 健康位转不健康。
  这是 R-01 的风险所在 —— 一个**不看上游**的判据天生更容易变成永远绿。
- **V-02b** ❌ **反向确认**：全部 L1 不可服务时，代理健康位**保持健康**。
  这一条与 V-02 同等重要 —— 它证明职责划分真的落地了，而不只是写在文档里。
- **V-03** ✅ **两个 Primary 全停的 554 秒窗口实测通过（2026-09-11）**：
  五个边界的入口各 **10 笔真实交易全部确认**、各 20 次读请求，
  **5xx 零次、连接失败零次**。高度 837 → **887**（正好 50 个区块）。

  **这是一次差分，不只是一次通过。** 同一场景 2026-09-10 产生的是间歇性 502，
  而条件**没有任何变化** —— 窗口期间五个 L1 自报的综合健康位**仍然全部 503**：

  | | 2026-09-10（旧探测） | 2026-09-11（新探测） |
  |---|---|---|
  | 五个 L1 的 `/ext/health` | 503 | **503（照样）** |
  | 代理日志 `GET /ext/health` | 每 10 秒一条 | **0 次** |
  | `no live upstreams` | 多次 | **0 次** |
  | `upstream … temporarily disabled` | 一条请求连四行 | **0 次** |
  | 502 应答 | 有 | **0 次** |
  | 从入口发交易 | 发不出去 | **50/50 确认** |

  唯一的变化是**探测不再接触上游** —— 于是没有任何东西在制造上游失败，
  惩罚期永远是空的。三个故障转移参数一个字符都没动。
