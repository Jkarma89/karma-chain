## 第 0 节：分家的判据是**一个问题**，不是一张字段清单

> 改了这个字段，**已经存在的链上状态还有没有意义**？

- **有意义** → 部署描述 → 移出，不进 stamp，改它不重置
- **没意义** → 协议参数 → 留下，stamp 保护，改它必须重置

**把这个问题写在最前面，是因为字段清单会过期而问题不会。**
日后新增字段时，先回答这个问题，再决定它落在哪一侧。

### 逐字段归属

| 字段 | 归属 | 理由 |
|---|---|---|
| `name` / `environment` | 协议 | 链的自我描述 |
| `configVersion` | 协议 | stamp 的第一项 |
| `chain.*`（chainId / blockchainName / reservedMainnetChainId） | 协议 | 改了就是另一条链 |
| `avalanche.networkId` | 协议 | 同上 |
| `avalanche.*Version`（avalanchego / subnet-evm / CLI） | 协议 | **边界情形** —— 它是组件版本不是链身份，但换 VM 可能改变状态转移（宪法第十五条的 "VM Behavior"）。**按更重的那一侧归** |
| `nativeToken` / `feeConfig` / `allowFeeRecipients` / `blockProduction` | 协议 | 代币与 gas 规则 |
| `devAccounts` | 协议 | 进创世分配 —— 创世 sha256 本来就在 stamp 里 |
| `validators.management` / `ownerAccount` | 协议 | PoA 的治理主体，属链上权限 |
| **`topology`**（activeDeployment / nodes / deployments） | **部署** | 哪几台机器、怎么划边界 |
| **`endpoints.hostRpcPort` / `publishedHosts`** | **部署** | 端口与主机名 |
| **`endpoints.rpcPath`** | **部署** | **边界情形** —— 访问路径，但由 `blockchainName` 派生。移出并**加一条一致性守卫** |
| **`validators.nodes[]`**（httpPort / stakingPort / keyDir） | **部署** | 端口与密钥位置 |
| **`validators.count`** | **部署** | 降级为**期望成员数**（见第 2 节） |
| **`primaryNetwork.nodeCount`** | **部署** | 同上 |

> **历史佐证**：`configVersion` 递增过四次，**三次是上表右半边的改动**
> （1.2.0 加 `publishedHosts`、1.3.0 加 `topology`、1.4.0 改端口）。
> 每一次都丢掉了当时全部链上状态 —— 而链的身份一个字节都没动。

## 第 1 节：`Deployment`（部署描述）

移出后的新实体。**它自己的版本号不进 stamp。**

| | |
|---|---|
| 内容 | 上表右半边的全部字段 |
| 版本 | 自己的（与 `configVersion` 无关） |
| 改动后果 | 重新渲染生成物 + 在受影响的机器上重建容器；**链不停、不重置** |
| 校验 | 自己的 JSON schema；T-5 与地址唯一性等业务约束照旧 |

### 必须成立（可测）

- **D-1**：改 `Deployment` 后 stamp 六项**逐字节不变**（SC-001）
- **D-2**：分家前后全部生成物**逐字节相同**（SC-003）——
  这是"只搬家、不改行为"的机械证明
- **D-3**：协议参数文件里 **MUST NOT** 残留任何部署字段，且有守卫禁止它们回去（FR-005）
- **D-4**：`deriveTopology()` 的**输出形状逐字段不变** ——
  这是让 30+ 个消费者一行不改的关键（research R-02）

### 明确**不**成立

- `Deployment` **不**保证跨机原子更新。五台机器不是同时 `git pull` 的，
  中间态必须**可报出**（FR-008），而不是假装不存在。

## 第 2 节：`MemberSet`（成员集合）—— 事实来源在链上

| | |
|---|---|
| **实际成员** | 链上（PoA 合约的验证者集合 / P 链的权益持有者）—— **事实来源** |
| **期望成员** | `Deployment` 里的声明（`validators.count`、`topology.nodes`） |
| 两者不一致 | **必须可见**（FR-030） |

### 为什么文件不能是事实来源

本期之后成员是**运行期可变**的。文件回答不了「现在有几个验证者」——
它只能回答「我们打算有几个」。

**这与宪法第十六条不冲突**：第十六条要的是**协议参数**的唯一事实来源，
而成员集合在本期之后不再是协议参数。

### 漂移的呈现沿用既有形状

面板已经在做"声明 vs 观测"的比对 —— 节点自报的 NodeID 与声明对不上时报
`identity-mismatch`。**成员漂移是同一个形状，扩既有那套，不新建一套。**

三种漂移各有不同处置：

| 漂移 | 含义 | 处置 |
|---|---|---|
| 链上有、声明里没有 | 有人绕过工具加了一个 | 补进声明，或把它退出 |
| 声明里有、链上没有 | 加入流程没走完，或退出只做了一半 | 看多步流程停在哪一步（FR-016） |
| 两边都有但属性不同（端口、边界） | 部署描述过期 | 更新声明 |

## 第 3 节：`f(n)` —— 容错函数

```
f(n) = 最大的 f 使 (n - f) / n ≥ 0.75
```

| n | 4 | 5 | 6 | 7 | 8 | 9 | 10 | 11 | 12 |
|---|---|---|---|---|---|---|---|---|---|
| **f** | 1 | 1 | 1 | 1 | **2** | 2 | 2 | 2 | **3** |

### 这张表有两个会让人做错决定的地方

1. **加节点不一定提高容错。** 5 → 6 → 7 都是 f=1。
   要提高必须跨过 8 这一格。**面板与工具不得暗示"节点更多了就更抗"**（FR-025）。
2. **减节点可能砍半容错。** 8 → 7 让 f 从 2 掉到 1。
   而名册少一个看着无关紧要 —— **所以退出操作必须在动手前把这个说出来**（FR-011）。

### 为什么每一格都要有测试

003 的 `contracts/health-tier.md` 第 4b 节记着一次**错误外推**：
从 n=5 的"4/5 = 80% 是零余量"推出"n=9 时 8/9 是零余量" —— **推错了**
（n=9 的 f 是 2，掉 1 个仍有余量）。那次是自己写的测试抓出来的。

**本期扩容缩容会走遍这些 n，所以 n=4…12 逐格都要有断言**（FR-024 / V-17）。

## 第 4 节：`MembershipChange`（一次成员变更）

多步、可失败、可重试。**执行前必须把容错代价说清。**

| 阶段 | 内容 |
|---|---|
| **前置检查** | 创世哈希一致（FR-014）、T-5 不越界（FR-013）、恢复能力可用（FR-015）、当前链是否健康 |
| **代价告知** | `n: A → B`，`f(A) → f(B)`；`f` 下降时要求显式确认（FR-011） |
| **执行** | 合约调用 → Warp 消息 → P 链交易 → 合约确认（ACP-77） |
| **收尾** | 更新期望成员声明；核对链上实际成员 |

### 每一步失败都要可见可重试（FR-016）

这是一个**多步、跨系统**的流程 —— 合约在 L1、注册交易在 P 链、两者靠 Warp 消息连起来。
中间任何一步失败，链上都可能留下**半注册状态**。

**判据不是"不会失败"，是"失败时能说出停在哪一步"**（V-10：每一步人为注入失败）。

### 两条退出路径

| | 优雅退出 | 紧急摘除 |
|---|---|---|
| 前提 | 机器还活着、能配合 | 机器已损坏/失联 |
| 顺序 | **先从集合移除 → 等确认 → 再停进程** | 直接从集合移除 |
| 为什么顺序不能反 | 先停进程再移除 = 制造一段"集合里有个死节点"的窗口，容错余量被白白吃掉 | — |
