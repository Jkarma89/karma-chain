## 起面板

```sh
# Linux / Git Bash
KARMACHAIN_DOMAIN=<本机边界> sh scripts/devnet-dashboard.sh

# Windows PowerShell
$env:KARMACHAIN_DOMAIN='<本机边界>'; .\scripts\devnet-dashboard.ps1
```

浏览器打开 `http://localhost:21680`。精简视图：`http://localhost:21680/?view=public`。

可选参数：`--port <n>`（默认 21680）、`--interval <秒>`（**默认 5**，上限 6）、`--deployment <名>`。

> **间隔与发现时延的关系**：发现时延 ≈ 间隔 + 一轮探测的最坏耗时。容器被 kill 时端口立即拒连，一轮很快（约 0.2s）；机器断电或静默丢包时要等满 4 秒探测超时。所以默认 5 秒下最坏约 **9.1 秒**，仍在 10 秒预算内但余量只剩约 0.9 秒 —— 这是 2026-09-10 从 2 秒调到 5 秒的代价，**上限 6 秒因此不能再放宽**。要更快发现就把间隔调小。

> **21680 为什么是默认值**：它在 Windows 动态端口范围（实测 1024–15000）与排除区间之外，与节点占用的 21650–21669 不重叠，并留在 002 已验证安全的两万段内。002 的节点端口曾因 Hyper-V 从动态范围切走整段而从 96xx 迁到 216xx（研究 R-08），这条教训直接决定了此处的取值。
>
> **面板端口刻意不在 `protocol.json` 里**：项目约定"任何字段变更须递增 `configVersion`"，而 `configVersion` 在出生证明的六项比对之列 —— 加一个字段就等于七个节点退出码 12 拒绝启动、五台机器全链重置。研究 R-03。

## 场景 D —— 单链路故障：不得误报节点下线

**验**：SC-005 —— **这是报警可信度的核心场景**

002 的 ubuntu-1 线缆丢包（21–27%）就属这一类：朴素面板会误报"节点下线"并触发"链已停止"的假报警，而链完全正常。

**制造方法**（在**观察者**机器上，只阻断到某一个节点 HTTP 端口的出向连接；**不动** staking 端口，其余节点因此仍看得见它）：

```powershell
# Windows（观察者）
New-NetFirewallRule -DisplayName "km-test-block-l1-3" -Direction Outbound `
  -RemoteAddress 192.168.1.21 -RemotePort 21664 -Protocol TCP -Action Block
# 撤销
Remove-NetFirewallRule -DisplayName "km-test-block-l1-3"
```

```sh
# Linux（观察者）
sudo iptables -I OUTPUT -d 192.168.1.21 -p tcp --dport 21664 -j DROP
# 撤销
sudo iptables -D OUTPUT -d 192.168.1.21 -p tcp --dport 21664 -j DROP
```

| 期望 | 判据 |
|---|---|
| 该节点标为「**本机视角不可达**」，而非「节点下线」 | FR-019 / FR-004a |
| 文案说明"其余 N 个节点仍报告看得见它 —— 是本机到它的网络路径问题" | FR-019 |
| 健康度保持 **100%**、余量保持 **1**、**全程不报警** | FR-012 / SC-005 |
| 异常分类为 `observation`，处置指向"修本机网络，别去动那台机器" | FR-022 |

> **注意**：Windows 的 WFP 对被封端口是**静默丢弃**（不回 RST），002 实测过 —— 所以面板会等满 4 秒探测超时。这是预期行为，不是面板的问题。

### 更简单的等价做法（自动化用的就是这条）

不用防火墙，用既有的 `KARMACHAIN_ADDRESS_OVERRIDE`（002 T060 引入）把某个边界的地址
指向 **TEST-NET-1**（`192.0.2.0/24`，RFC 5737 保留给文档用途，保证不可路由）：

```sh
KARMACHAIN_ADDRESS_OVERRIDE="win-2=192.0.2.1" sh scripts/devnet-dashboard.sh
```

于是：**观察者**按那个地址探不到该节点，而**节点本身分毫未动** —— 仍在正常出块，
仍出现在其余节点的对等列表里，于是 `seenByPeers` 里有它的 NodeID，classify 判
「本机视角不可达」。这正是链路故障的语义。

比防火墙规则好在三点：不需要管理员权限、跨平台一致、**不会因为忘了撤销规则而留下后患**。
`tests/e2e/dashboard-link-fault.test.mjs` 用的就是这条路，2026-09-10 实测通过
（l1-2 标为本机视角不可达、健康度保持 100%、撤销后回到 `healthy/768`）。

## 场景 E —— 观察者失明：不得报「链已停止」

**验**：SC-006、FR-020

**制造方法**：在观察者机器上禁用网卡（或拔掉网线）几十秒。

| 期望 | 判据 |
|---|---|
| 面板呈现「**失去观测能力**」 | SC-006 |
| **全程不出现「链已停止」的表述** | FR-020 —— 出现即为失败 |
| 提示先检查本机网卡与交换机 | FR-020 |
| `pathAlive` 佐证结论出现：五台机器端口全无应答 → "更像本机网络问题" | `data-model.md` 第 2 节 |
| 恢复网卡后自动回到 100%，无需刷新页面 | — |

> **这一条为什么最容易实现错**：既有 `summarize()` 在 0/7 可达时会输出「链已停止出块」—— 那是它孤立使用时的**正确**行为（`devnet-status` 是人主动跑的一次性命令，人知道自己刚拔了网线）。面板必须在它之上加一层（判定优先级 P1）。若这一层缺失或放错顺序，本场景就会变成假报警。
