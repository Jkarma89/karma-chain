# Feature Specification: 崩溃可恢复、可跨机部署的验证者网络

**Feature Branch**: `002-resilient-validator-network`

**Created**: 2026-09-06

**Status**: Draft

**Input**: User description: "崩溃可恢复、可跨机部署的 KarmaChain 验证者网络 —— 强制重启 Docker Desktop 后开发网无法启动，节点数据库完好但 Avalanche CLI 的编排账本丢失，唯一出路是丢弃全链状态重置。需要消除对编排工具的运行时依赖（缺陷 A）与零物理冗余（缺陷 B）。"

## 背景与目标

### 触发事件

2026-09-05，宿主机的容器运行时（Docker Desktop）被强制重启。之后开发网无法启动：等满 300 秒超时后以退出码 20 失败，提示"L1 验证者没有回来"。事后取证：

| 证据 | 状态 |
|---|---|
| 5 个 L1 验证者的数据库 | **完好**，各 192 KB |
| 2 个 Primary 节点的数据库 | **完好**，各 40 KB |
| 编排工具的快照目录 | **空**（一个快照都没有） |
| 编排工具的网络注册表 | 指向一个已经死掉的运行目录 |
| 唯一可行的恢复手段 | 丢弃全部链上状态、从创世重建 |

**链上数据一秒都没丢；丢的是"怎么把这些健康的节点重新拉起来"这份记账。**

### 两个彼此独立的缺陷

**缺陷 A —— 链状态的存续依赖一次成功的优雅停止。**
当前全部 7 个节点是单一运行单元内由编排工具管理的进程。链状态要活到下一次启动，必须满足一条链式条件：运行单元收到终止信号 → 编排工具及时收到并完成快照写入 → 进程才退出。任何绕过该路径的终止——强制重启容器运行时、宿主断电、强制杀进程、内存耗尽——都必然使链回到"只能重置"的状态。

这一缺陷与节点是否分布**无关**。即便把节点摊到多台机器上，只要每台机器上的运行时仍由该编排工具负责拉起，每台机器都会各自重现同一故障。

**缺陷 B —— 零物理冗余。**
5 个验证者是同一运行单元内的 5 个进程，共享同一个宿主、同一份文件系统、同一个进程生命周期。"单机故障导致全链停止"在此拓扑下不是风险，是必然。

### 目标

一条区块链不应该因为一台机器的故障而全链重置。本特性要求：

1. 任何节点被强制终止后，重启即可从自身数据恢复并重新入网，**不需要快照、不需要重置、不需要人工干预**。
2. 链的持续运行不再取决于任何一次停止是否"优雅"。
3. 验证者可以摊到多个会独立失效的物理边界上，任一边界整体失效时链继续出块。
4. 编排工具退出运行时路径，只保留一次性建链的角色。

### 与既有决策的关系

- `docs/adr/README.md` 中的待决事项 **"validator decentralisation path"** 即本特性，现予以立项。
- ADR 已记录：当前所用的 Avalanche CLI v1.9.6 处于**维护模式 / 已弃用**。本特性把它从运行时路径上摘除，使该弃用不再构成运行风险。
- 001 的研究结论（`research.md` R-05）已给出容错上限的源码依据，本特性沿用并要求实测复核。

> **需求编号约定**：本文的 `FR-0xx` / `SC-0xx` 属于 002。引用 001 的条目时写作 `001 FR-0xx`。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 强制终止后链自己回来 (Priority: P1)

开发者在链上有交易和已部署的合约。宿主机的容器运行时崩溃、被强制重启，或者整机断电。开发者重新启动开发网，链从中断前的高度继续，之前的交易、合约、余额都还在。整个过程不需要执行重置，也不需要理解节点内部发生了什么。

**Why this priority**: 这是触发本特性的真实故障，也是"不能因为一台电脑故障就全链重置"这一诉求的最小可交付形态。单独实现它就已经消除了当前唯一的数据丢失路径。

**Independent Test**: 启动开发网 → 发送若干交易使高度到达 H、部署一个合约 → 以最粗暴的方式终止全部节点（强制杀进程，不发送终止信号）→ 重新启动 → 断言高度 ≥ H、创世哈希不变、该合约的代码与存储仍可读取。全程不执行重置命令。

**Acceptance Scenarios**:

1. **Given** 链处于高度 H 且有已部署的合约，**When** 全部节点被强制杀死（不经过任何优雅停止）后重新启动，**Then** 链在无人工干预下恢复，高度 ≥ H，创世哈希不变，合约代码与存储可读。
2. **Given** 链处于高度 H，**When** 宿主机的容器运行时被强制重启，**Then** 重新启动开发网后链从 H 继续，且启动过程不报告任何需要重置的错误。
3. **Given** 链已恢复，**When** 运行既有的验证命令，**Then** 全部既有检查通过。
4. **Given** 曾发生过强制终止，**When** 开发者查看启动输出，**Then** 输出明确告知这是一次崩溃恢复以及恢复到的高度，而不是静默进行。

### User Story 2 - 一个验证者挂掉，链照常出块 (Priority: P1)

运维人员停掉、杀死或隔离单个验证者节点。链继续接受交易并出块，其他节点不受影响。该验证者重新启动后自动追上当前高度，重新参与共识，无需任何人工修复。

**Why this priority**: 这是"冗余"从纸面变成事实的证明。它在单机上就可验证，是跨机部署的前置能力——如果单个节点重启后不能自愈，摊到多台机器上只会让问题更难查。

**Independent Test**: 5 个验证者全部健康时记录高度 → 强制杀死其中 1 个 → 持续发送交易并观察链继续出块 → 重启该节点 → 断言它在限定时间内追平高度并恢复健康。

**Acceptance Scenarios**:

1. **Given** 全部验证者健康，**When** 任意 1 个验证者被强制终止，**Then** 链继续接受交易并出块，且状态输出把该节点标记为不可用而非把整条链标记为故障。
2. **Given** 1 个验证者已离线一段时间，**When** 它重新启动，**Then** 它从自身数据恢复、从对等节点补齐缺失区块，并在限定时间内追平当前高度。
3. **Given** 离线的验证者数量超过容错上限，**When** 客户端发送交易，**Then** 链停止出块而不是分叉或产生前后不一致的状态；恢复到上限之内后自动继续出块，且此前已确认的区块不被回滚。
4. **Given** 某个验证者正在追赶，**When** 运维查看状态，**Then** "正在追赶"与"故障"是两种可区分的状态，并给出追赶进度。

### User Story 3 - 运行时不再依赖编排工具 (Priority: P2)

系统管理员启动、停止、重启任意节点或整个网络，全过程不调用那个已进入维护模式的编排工具。该工具只在**第一次建链**时使用一次，其产出（子网标识、区块链标识、链别名、初始验证者集合）被固化成版本控制下的制品，此后只读。

**Why this priority**: 这是缺陷 A 的结构性修复，也是 US1、US2 得以成立的原因。它同时消除了一个已弃用依赖带来的长期风险——上游停止维护时，我们的运行时不受影响。

**Independent Test**: 在不包含该编排工具的运行环境中启动全部节点，链正常出块、既有验证全部通过。再检查运行时代码路径中不存在对该工具的任何调用。

**Acceptance Scenarios**:

1. **Given** 建链制品已固化在仓库中，**When** 在一个不含该编排工具的运行环境里启动全部节点，**Then** 网络正常起来，既有验证全部通过。
2. **Given** 网络正在运行，**When** 停止并重新启动它，**Then** 全过程无任何该工具的调用，链高度延续。
3. **Given** 有人重新执行一次性建链，**When** 产出与仓库中已固化的制品比较，**Then** 创世哈希、Chain ID、Network ID、开发账户余额完全一致。

---

### User Story 4 - 一整台机器挂掉，链继续出块 (Priority: P2)

验证者部署在多个会独立失效的物理边界上（不同机器 / 不同虚拟机 / 不同宿主）。其中任意一个边界整体失效——断电、断网、被关机——链继续接受交易并出块。该边界恢复后，其上的节点自动追平并重新参与共识。

**Why this priority**: 这是缺陷 B 的修复，也是用户诉求的最终形态。它排在 US1–US3 之后，因为它需要"节点能独立启停并自愈"作为前提，且需要额外的硬件与网络条件。

**Independent Test**: 把验证者按声明的边界划分部署 → 使任意一个边界整体不可达 → 持续发送交易并断言链继续出块 → 恢复该边界 → 断言其上节点自动追平。

**Acceptance Scenarios**:

1. **Given** 验证者已按声明的故障边界分布，**When** 任意一个边界整体失效，**Then** 链继续接受交易并出块。
2. **Given** 某个边界曾整体失效，**When** 它恢复，**Then** 其上的全部节点自动追平当前高度，无需人工干预。
3. **Given** 一份把超过容错上限的验证者放进同一个故障边界的拓扑配置，**When** 启动系统，**Then** 系统拒绝启动，并明确指出违反了哪条约束、需要怎么改。
4. **Given** 跨边界部署，**When** 从零重建整套环境，**Then** 只需要克隆仓库加执行版本控制下的部署流程，不存在任何"只在某台机器上有"的手工配置。

---

### User Story 5 - 拓扑参数有唯一出处并可复现 (Priority: P3)

任何开发者或 AI Agent 依据 Git 仓库就能重建出拓扑完全一致的网络。验证者数量、故障边界划分、节点身份、引导节点集合、端点分配都来自同一份声明，节点配置由它生成而非手写。

**Why this priority**: 保证本特性不把宪法第七条（基础设施可复现）与第十六条（协议配置唯一事实来源）打破。它是约束性的，不新增用户可见能力，因此排在功能故事之后。

**Independent Test**: 修改声明中的拓扑参数并重新生成 → 断言全部派生的节点配置随之变化；手工改动任一生成物 → 断言漂移测试失败。

**Acceptance Scenarios**:

1. **Given** 拓扑声明发生变化，**When** 重新生成派生制品，**Then** 全部节点配置一致更新，无需手工修改任何一处。
2. **Given** 有人手工修改了某个生成的节点配置，**When** 运行漂移检查，**Then** 检查失败并指出偏离项。
3. **Given** 一份不满足容错约束的拓扑声明，**When** 校验它，**Then** 校验失败并说明违反了哪条约束。
4. **Given** 同一个仓库提交，**When** 在两台不同机器上分别重建，**Then** 创世哈希与节点身份完全一致。

---

### User Story 6 - 恢复过程对运维可见 (Priority: P3)

运维人员在故障与恢复期间能逐节点看到发生了什么：谁在运行、谁健康、谁在追赶、追到哪了、有几个对等节点、属于哪个故障边界。故障归入既有的失败分类体系，能据此判断该等待还是该处置。

**Why this priority**: 没有它，US1、US2、US4 的恢复过程是黑盒——运维无法区分"正在追赶，再等等"和"卡住了，需要动手"。但它依附于前面的能力，因此排 P3。

**Independent Test**: 制造单节点故障与恢复 → 断言状态输出在每个阶段都给出上述字段，且"追赶中"与"故障"可区分。

**Acceptance Scenarios**:

1. **Given** 网络正在运行，**When** 查看状态，**Then** 逐节点报告运行状态、健康、是否已完成引导、当前高度、对等节点数、所属故障边界。
2. **Given** 某节点正在追赶，**When** 查看状态，**Then** 它被标记为"追赶中"并给出进度，且不被计为故障。
3. **Given** 发生了故障，**When** 查看输出，**Then** 故障归入既有的九类失败类别之一（001 FR-030）；若需新增类别，该类别已在文档中显式声明。

### Edge Cases

- **节点在引导过程中途被强制终止** —— 重启后能否继续引导，还是需要清掉半成品状态重来？系统必须能自行判断并给出确定行为。
- **单个节点的数据确实损坏**（不是记账丢失，是数据库真的坏了）—— 该节点必须能被单独重建并从对等节点重新同步，**不影响其余节点**，也不需要全链重置。
- **全部节点的数据同时损坏** —— 这是唯一允许要求重置的情形，且必须明确告知这是数据损坏而非编排问题。
- **节点落后过多** —— 落后到超出对等节点保留的历史范围时，追赶策略是什么？必须有确定行为而非无限期挂起。
- **宿主休眠 / 挂起后恢复**（笔记本合盖、Docker Desktop 暂停）—— 节点感知到的时间发生跳变，必须能恢复而不是永久卡死。
- **跨机时钟不同步** —— 超出容忍范围时必须明确报错，而不是表现为随机的共识异常。
- **跨边界的节点间通信被阻断但节点仍在运行**（网络分区，非宕机）—— 少数侧必须停止出块而非独立推进，避免产生两条历史。
- **超出容错上限后恢复** —— 恢复出块时，此前已确认的区块不得回滚。
- **节点身份丢失**（staking 证书缺失或被换掉）—— 该节点不再被验证者集合承认，系统必须明确报出身份不匹配，而不是表现为"连不上"。
- **不同操作系统的宿主行为不一致**（路径语义、文件系统大小写、时间同步机制、进程终止语义）—— 差异必须由版本控制下的配置消除，而不是靠"某台机器上手工调过"。
- **某个故障边界的宿主不满足节点运行时的前置条件** —— 必须在部署前被识别并明确报出，而不是等到节点起不来才发现。
- **多个故障边界被同一外部事件同时打掉**（操作系统的统一更新重启窗口、同一路供电、同一台交换机）—— 声明的"独立失效"被悄悄破坏，超出容错上限而全链停摆。系统必须能从状态输出中看出这是同时失效而非级联故障；边界独立性的实际保障手段必须被显式记录。
- **宿主重启后容器运行时没有自动起来**（需要用户登录才拉起的运行时）—— 该边界会长时间缺席而无人察觉，必须能被状态输出识别为"边界缺席"而非"节点故障"。
- **协议参数变了但旧链数据还在** —— 既有的出生证明机制必须继续拦截（001 的退出码 12 语义不得回退）。
- **建链制品与链数据不一致**（比如制品来自另一次建链）—— 必须在启动早期被识别并拒绝，而不是等到超时。
- **快速连续重启**（反复强制杀死再启动）—— 不得进入需要人工干预才能退出的状态。
- **磁盘写满** —— 归入既有的 storage 失败类别，并且腾出空间后能恢复。

## Scope Boundaries

### In Scope

- 消除对"停止时保存快照"的依赖；节点从自身持久化数据崩溃恢复。
- 每个节点成为可独立启停、独立恢复的运行单元。
- 单故障边界内的崩溃自愈（阶段一）。
- 跨多个故障边界的部署与整域失效容忍（阶段二）。
- 一次性建链产出的固化，及运行时对编排工具的解除依赖。
- 拓扑与寻址参数纳入唯一事实来源，并接受漂移检查。
- 拓扑合法性校验（容错约束、故障边界分布）。
- 逐节点的状态与恢复进度可观测。
- 上述能力的验证扩展与文档。

### Out of Scope（后续独立功能）

- 主网部署、真实质押经济、验证者的经济激励。
- 验证者集合的增删治理流程（PoA 合约操作）—— 另立规格。
- 面向公网的 RPC 暴露、TLS、域名与反向代理 —— 属 `docs/adr/README.md` 中另一条待决事项。
- 监控告警系统、指标采集与看板（宪法第九条）—— 另立规格。
- 自动扩缩容、故障自动迁移、跨地域部署。
- 区块浏览器。
- 节点软件的滚动升级流程。
- 对既有 13 项验证之外的性能与吞吐优化。

## Requirements *(mandatory)*

### Functional Requirements

#### 崩溃恢复与持久性

- **FR-001**: 每个节点 MUST 拥有独立的持久化数据存储，其可用性 MUST NOT 依赖任何编排工具的额外记账。
- **FR-002**: 任一节点被非优雅终止（强制杀进程、宿主断电、内存耗尽）后重新启动，MUST 从自身数据恢复并重新加入网络，无需人工干预。
- **FR-003**: 全部节点同时被非优雅终止后重新启动，链 MUST 从终止前的高度继续，MUST NOT 回到创世。
- **FR-004**: 链状态的存续 MUST NOT 依赖停止时写出快照这一动作的成功。
- **FR-005**: 崩溃恢复路径 MUST NOT 要求执行重置。重置 MUST 仅作为开发者显式要求重建时的手段保留。
- **FR-006**: 单个节点的数据损坏 MUST 可通过单独重建该节点解决，MUST NOT 要求全链重置。
- **FR-007**: 系统 MUST 能区分"编排问题"与"数据确实损坏"，并只在后者且波及全部节点时才要求重置。

#### 容错

- **FR-008**: 当不可用的验证者数量在容错上限之内时，链 MUST 继续接受交易并出块。
- **FR-009**: 当不可用的验证者数量超过容错上限时，链 MUST 停止出块，MUST NOT 分叉或产生前后不一致的状态；恢复到上限之内后 MUST 自动继续出块，且已确认区块 MUST NOT 被回滚。
- **FR-010**: 重新启动的验证者 MUST 自动追平当前高度并重新参与共识，无需人工干预。
- **FR-011**: 系统 MUST 明确声明当前拓扑的容错上限（可容忍的验证者数量与故障边界数量），且该声明 MUST 可被自动化验证。
- **FR-012**: 容错上限 MUST 经实测复核，而不仅依据上游默认参数推导。001 `research.md` R-05 已依据源码给出"5 个等权验证者可容忍 1 个离线"的结论（判据为发起查询所需的已连接权重比例 = 共识法定人数 ÷ 采样规模），本特性 MUST 以实测确认该结论在新拓扑下依然成立。

#### 解除运行时对编排工具的依赖

- **FR-013**: 编排工具 MUST 仅用于一次性建链。其产出（子网标识、区块链标识、链别名、初始验证者集合）MUST 固化为版本控制下的制品。
- **FR-014**: 节点的启动、停止、重启路径 MUST NOT 调用该编排工具。
- **FR-015**: 系统 MUST 能在不包含该编排工具的运行环境中启动全部节点，且该性质 MUST 可被自动化验证。
- **FR-016**: 节点身份 MUST 由持久化的身份材料决定，重启后 MUST 保持不变。
- **FR-017**: 当建链制品与既有链数据不一致时，系统 MUST 在启动早期拒绝并说明原因，MUST NOT 等待至超时。

#### 拓扑与部署

- **FR-018**: 每个节点 MUST 是可单独启动、停止、重启的运行单元。
- **FR-019**: 故障边界的划分与节点归属 MUST 是显式的声明，MUST NOT 隐含于部署方式。
- **FR-020**: 5 个验证者 MUST 分布在 **5 个故障边界**上，每个边界恰好 1 个验证者。任一边界整体失效时（剩余 4 个验证者，占权重 80% ≥ 75% 的查询门槛），链 MUST 继续接受交易并出块。
- **FR-021**: 系统 MUST 拒绝违反容错约束的拓扑声明。在 5 验证者拓扑下，任一故障边界内的验证者数量 MUST NOT 超过 1 个；违反时 MUST 指出是哪个边界、放了几个验证者、上限是多少。
- **FR-022**: 跨机部署 MUST 通过版本控制下的配置完成，MUST NOT 依赖任何手工步骤（宪法第七条）。
- **FR-023**: 节点之间的通信 MUST 在跨故障边界时同样成立，其所需的寻址信息 MUST 来自声明而非运行时探测的偶然结果。

#### 连续性（不得回退既有能力）

- **FR-024**: 创世哈希、Chain ID、Network ID、6 个开发账户的创世余额 MUST 保持不变。
- **FR-025**: 既有的 13 项验证检查 MUST 继续全部通过。
- **FR-026**: 既有的出生证明机制（协议参数与链数据不一致时拒绝启动并以约定退出码报错，001 FR-021）MUST 继续有效。
- **FR-027**: 新增的拓扑、寻址、故障边界参数 MUST 由既有的唯一事实来源派生（宪法第十六条），并 MUST 被漂移测试覆盖。
- **FR-028**: 面向第三方的公开制品 MUST NOT 泄漏内部路径、验证者身份材料、内部组件版本。
- **FR-029**: 提交进仓库的开发用身份材料 MUST 满足宪法第四条 v1.1.0 例外条款的全部四项条件，且 MUST NOT 出现在任何主网路径上。
- **FR-030**（2026-09-07 修订，理由见 SC-007）: 从克隆仓库到得到一条可用的链，人工步骤 MUST NOT 多于 **3 步**（克隆 + 一次性建链 + 启动）；**建链之后**的每次启动 MUST 为 **1 步**，且 MUST NOT 要求任何额外的人工判断（例如"这次要不要恢复快照"）。

#### 可观测性

- **FR-031**: 状态输出 MUST 逐节点报告：运行状态、健康、是否已完成引导、当前高度、对等节点数量、所属故障边界。
- **FR-032**: "正在追赶"MUST 与"故障"是两种可区分的状态，且追赶状态 MUST 给出进度。
- **FR-033**: 启动时若判定为崩溃恢复，MUST 明确告知这是崩溃恢复及恢复到的高度，MUST NOT 静默进行。
- **FR-034**: 本特性引入的故障 MUST 归入既有的九类失败类别（001 FR-030）；若需新增类别，MUST 在文档中显式声明并说明判据。

### Key Entities

- **节点（Node）**：网络的最小运行与故障单元。属性：身份（由持久化身份材料决定，重启不变）、角色（主网络节点 / L1 验证者）、独立的数据存储、所属故障边界、对外端点。
- **故障边界（Failure Domain）**：一组会同时失效的节点的边界（同一台机器、同一台宿主、同一处供电）。属性：标识、成员节点集合。是拓扑声明的一部分，不是部署方式的副产品。
- **拓扑（Topology）**：验证者数量、故障边界划分及成员归属、引导节点集合、端点分配、由上述推导出的容错上限。派生自唯一事实来源。
- **链身份制品（Chain Identity Artifact）**：一次性建链的产出——子网标识、区块链标识、链别名、初始验证者集合。固化后只读，用于校验链数据的归属。
- **验证者集合（Validator Set）**：PoA 下被承认的验证者成员及其权重。节点身份必须与之匹配才能参与共识。
- **恢复状态（Recovery State）**：单个节点在崩溃后的处境——已恢复 / 引导中 / 追赶中（含进度）/ 身份不匹配 / 数据损坏。是"该等待还是该处置"的判断依据。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在宿主容器运行时被强制重启的场景下，开发网重新启动后恢复到中断前的区块高度，**无需任何人工干预、无需重置**，恢复耗时不超过 5 分钟。
- **SC-002**: 在 50 次连续的"强制终止 → 重新启动"循环中，链状态丢失次数为 **0**，需要重置的次数为 **0**。
- **SC-003**: 任意单个验证者不可用时，链继续出块的成功率为 **100%**（连续 30 分钟、每分钟至少一笔交易的观测窗口内）。
- **SC-004**: 被强制终止的单个验证者重新启动后，追平当前高度的耗时不超过 **2 分钟**。
- **SC-005**: 5 个故障边界中任意 1 个整体失效时，链继续出块的成功率为 **100%**（连续 30 分钟、每分钟至少一笔交易的观测窗口内）；该边界恢复后其上节点在 **2 分钟**内自动追平，无需人工干预。
- **SC-006**: 超出容错上限时链停止出块，恢复到上限内后自动继续，且**已确认区块回滚数量为 0**。
- **SC-007**（2026-09-07 修订，见下）: 从克隆仓库到得到一条可用的链，人工步骤为 **3 步**（克隆 + 一次性建链 + 启动）；此后每次启动为 **1 步**。整条路径的耗时不超过原基准的 **1.5 倍**（≤ 120 秒）。

  > **修订理由。** 原判据要求 2 步（克隆 + 一条启动命令），与 001 持平。实现后实测为 3 步 ——
  > 多出的是 `scripts/devnet-bootstrap`。这不是实现偷懒，而是架构性的：Subnet 与 Blockchain 是
  > **P 链上的交易**，只存在于节点数据库里，而数据卷不进 git。仓库里能提交的只有建链的**产物**
  > （SubnetID / BlockchainID，即"第二类事实"，见 ADR-0009），产物指向的那条链本身必须在本地
  > 真的建出来一次。
  >
  > 曾考虑让 `devnet-start` 在"制品在、P 链上没有那条链"时自动建链一次以恢复 2 步，未采纳：
  > 那会把"一次性建链"与"日常启动"两件性质不同的事合进同一个命令，换来的只是少敲一行，
  > 而"在 P 链上创建 Subnet 与 Blockchain"值得让人显式触发。
  >
  > 耗时口径原本就达标（建链约 80s + 首次启动 5–15s ≈ 95s ≤ 120s），且**日常启动反而更快**：
  > 001 的冷启动 80s / 快照恢复 16s，002 每次启动 5–15s（各节点从自身数据卷恢复）。
  > 也就是说这次修订放宽的是一次性成本，不是日常成本。

  > **判据边界的澄清（2026-09-09，跨机首次部署之后补）。** "人工步骤"指**克隆之后**
  > 为得到一条可用链而必须执行的操作，**不含机器前置条件**（装 Docker、装 git／curl、
  > 开放入站端口、Windows 的 PowerShell 执行策略）—— 那些与 001 的"装 Docker"同类，
  > 归 `docs/devnet.md` §1 与 §9.2，不计入本判据。
  >
  > 据此，2026-09-08 在干净机器上暴露的两件事分属两侧：
  > * **Windows 执行策略**（默认 `Restricted`，`.ps1` 一律不让跑）→ 前置条件，不违反 SC-007。
  > * **`scripts/*.sh` 在 git 里记成 `100644`**（NTFS 没有权限位）→ **真违反**：Linux 上
  >   克隆完必须先 `chmod +x` 才能开始，那就是第 4 步。已在 `604e459` 修正（改记 `100755`，
  >   并加双向守卫：入口 755、被 source 的公共件 644），SC-007 因此是被**恢复**而非被打破。

- **SC-008**: 创世哈希在全部部署形态（单边界、多边界、不同机器）下**完全一致**。
- **SC-009**: 既有 13 项验证检查通过率 **100%**。
- **SC-010**: 运行时路径中对编排工具的调用次数为 **0**，且在不含该工具的运行环境中启动成功率为 **100%**。
- **SC-011**: 任何一次单节点数据损坏，均可通过只重建该节点解决，**全链重置次数为 0**。
- **SC-012**: 故障与恢复期间，运维能在状态输出中区分"追赶中"与"故障"的准确率为 **100%**。

## Assumptions

- **环境限定为开发网**。主网的部署形态、质押经济、验证者治理均不在本特性范围内；本特性建立的可复现与冗余性质是主网的前置能力，但不等于主网就绪。
- **验证者数量维持 5 个**。阶段二选定 5 个故障边界、每边界 1 个验证者，该组合满足容错约束 $\lceil 5/5 \rceil = 1 \le 5/4$，因此**不需要调整验证者数量**，不触发宪法第十五条的协议变更流程。
- **阶段二的 5 个故障边界为 5 台独立机器**：**2 台 Windows + 3 台 Ubuntu 22.04 LTS**，每台承载 1 个验证者。宿主的操作系统前置条件已确定为"能运行 Docker Engine 24+ 与 Compose v2"——节点运行在容器内，宿主的 glibc 与发行版年龄不参与约束（`docker/devnet/Dockerfile` 的基底为 Debian trixie-slim）。Ubuntu 22.04 LTS 满足该条件。跨操作系统的一致性 MUST 由版本控制下的配置保证，而非逐台手工调整。
- **故障边界的独立性需要主动维护，不是买了 5 台机器就自动成立**。操作系统的统一更新重启窗口、共用供电、共用交换机都会让多个边界被同一事件同时打掉，从而突破容错上限。保障手段（错开更新窗口、供电与网络路径的隔离程度）MUST 在 `/speckit-plan` 阶段显式确定并记入 ADR。
- **Windows 边界与 Linux 边界的可用性特征不同**：Windows 上的容器运行时需要用户登录后才启动，Linux 上由系统服务在开机时拉起。该差异 MUST 在部署方案中显式处理，不得默认两者行为一致。
- **2 个 Primary Network 节点不构成单点**（2026-09-06 实测，research.md R-09 / V-08）：它们全部停止时 L1 照常出块。因此它们的边界归属可自由安排，不影响验证者的容错计算，也无需为它们追加冗余。
- **验证者数量不影响 EVM 创世**。因此调整验证者拓扑不会破坏 FR-024 对创世哈希的要求。
- **单容器模式将被替换而非并存**。同时维护两套编排方式会使漂移检查与验证矩阵翻倍，不符合宪法第十三条的选型克制。阶段一完成后，原单容器路径退役。
- **阶段一的故障边界数量为 1**。它解决缺陷 A（崩溃自愈），不解决整机失效；阶段二引入多个边界解决缺陷 B。两个阶段各自有独立的验收边界，阶段一可单独交付并具备完整价值。
- **对外 RPC 的暴露方式沿用现状**（本机与局域网，地址由运维告知）。公网暴露、TLS、域名属另一条待决事项，不因本特性而改变。
- **节点软件版本在全部节点上一致**。混版本运行与滚动升级不在范围内。
- **跨机时钟由宿主的时间同步机制保证**，本特性只要求在超出容忍范围时明确报错。
- **阶段二所需的多台机器由开发者自备**，可以是物理机、虚拟机或独立宿主，只要它们会独立失效。
- **既有的九类失败分类体系（001 FR-030）继续适用**，本特性优先复用而非新增类别。
