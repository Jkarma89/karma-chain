## 四、已裁定：从克隆到可用链由 2 步变 3 步（SC-007 / FR-030 已修订）

> **裁定结果（2026-09-07，项目负责人）：接受 3 步，修订判据。**
> spec.md 的 SC-007 与 FR-030 已相应修订，并在其中写明理由与被否决的替代方案。
> 本节保留原始分析，作为该修订的依据记录。


**事实**：001 是 `git clone` + `scripts/devnet-start`（R-14 实测基准 2 步）。
002 是 `git clone` + `scripts/devnet-bootstrap` + `scripts/devnet-start` = **3 步**。

**为什么会这样**：建链制品（SubnetID／BlockchainID）提交在仓库里，但 Subnet 与 Blockchain 是
**P 链上的交易**，只存在于节点数据库里 —— 而数据卷不在 git 里。因此新克隆的仓库必须先建链一次。
这不是疏忽，是"制品是第二类事实"（[ADR-0009](../../../docs/adr/0009-chain-identity-as-second-class-fact.md)）
的直接后果。

**耗时口径是达标的**：建链约 80s（一次性）+ 首次启动 5–15s ≈ 95s ≤ 120s（基准 80s 的 1.5 倍）。
不达标的只有步骤计数。

**当时提出的两条出路**：

1. **让 `devnet-start` 在"制品在、P 链上没有那条链"时自动建链一次。** 恢复 2 步。
   代价：`devnet-start` 会在首次运行时调用建链镜像（含 CLI）。它仍不在**运行时**路径上
   （建链只发生一次），但会削弱"建链是一次显式的、有意识的动作"这一设计意图，
   并与当前那道给出 `stop → bootstrap → start` 指引的守卫冲突。
2. **接受 3 步，修订 SC-007。** 代价：一条成功判据被放宽；需在 spec 中说明理由
   （P 链状态无法进 git，这是架构性的，不是实现偷懒）。

**已采纳第 2 条**（项目负责人裁定，2026-09-07）。第 1 条把两件性质不同的事
（一次性建链 vs 日常启动）合进同一个命令，换来的只是少敲一行；而"建链会在 P 链上创建
Subnet 与 Blockchain"这件事，值得让人显式触发一次。

**修订后要盯住的是"日常成本"而非"一次性成本"**：FR-030 修订稿因此加了一条原先没有的要求
——建链之后的每次启动 MUST 为 1 步，且不得要求任何额外的人工判断（例如"这次要不要恢复快照"）。
001 恰恰在这一点上有隐性成本：崩溃之后要人判断该 start 还是该 reset。002 消除了那个判断，
这是修订不该丢掉的部分。

**该条已实测**（2026-09-07）：

| 前一次如何结束 | 命令 | 耗时 |
|---|---|---|
| `devnet-stop` 正常停止 | `scripts/devnet-start` | 17s |
| `docker kill` 全部容器（强制终止） | **同一条命令，无需任何判断** | 17s |

两条路径的命令与耗时完全相同 —— "上一次是否优雅停止"对本次启动不再有任何影响。

### 跨机首次部署暴露的缺陷（21 项，按**类别**记）

这些缺陷**在单机形态下全部不可见**。单机形态跑了几十次、测试长期全绿，
而它们无一被触发 —— 记下来是为了让下一个特性别再靠"部署一次才发现"。

**A. 只在干净的新机器上才暴露的前置条件（4 项）**
`scripts/*.sh` 在 git 里记成 `100644`（NTFS 无权限位）；Windows 的 PowerShell 执行策略
默认 `Restricted`；构建容器的 DNS 解析不了（守护进程能拉镜像 ≠ 构建容器能解析）；
`docker info` 的权限错误被报成"守护进程没在运行"。
**共性**：开发机上早已配好，于是它们成了既成事实，没人再想起它们是前置条件。

**B. 写死了单机形态的假设（7 项）**
`devnet-verify` / `devnet-contracts` / `devnet-status` 写死 `--network karmachain`；
`crash-during-bootstrap` 写死 `local-local.yml`（**不报错，而是按单机配置重建节点**）；
`devnet-status` 拿本机同名残留容器描述**远端**节点；6 个故障注入测试按下标从全局列表挑靶子；
"故障没扩散"用"容器是否 running"判断。
**共性**：单机形态下"所有容器都在本机"恒真，于是这个假设从未被写出来，也就无从被质疑。

**C. 守卫是绿的，而被守的东西是坏的（4 项）**
`Invoke-Quiet` 守卫只检查"没用 `2>$null`"，而 helper 本身拦不住终止性错误；
`--concurrency` 守卫只检查字符串在不在，而那个标志名根本不存在（`node: bad option`）；
FR-026 的脱敏测试自 T080 起**永久跳过**（存活判据找的是已退役的容器）；
挂载新鲜度守卫写完了函数却**忘了调用**。
**共性**：守卫检查的是**字面或间接迹象**，不是**机制的行为**。四处现在都配了行为断言并反向验证。
**下次的自检问题：这条守卫如果坏了，它会变红吗？**

**D. 平台差异掩盖了缺陷（3 项）**
Docker 对**单文件** bind mount 绑 inode，Linux 上 `git pull` 后容器看不见新配置，
而 Docker Desktop 按路径解析所以 Windows 上不可见（**出生证明守卫因此有盲区**，
见 `contracts/node-runtime.md`）；Git Bash 把容器内绝对路径改写，导致 `docker exec` 静默失败
（本会话踩了 4 次，其中一次让 `selfState` 在 Windows 上恒为空）。
**共性**：本项目是"Windows 开发 + Linux 部署"，这正是平台差异最容易藏东西的组合。

**E. 测试基础设施本身（3 项）**
`test:e2e` 与 `test:integration` 缺 `--test-concurrency=1`（node 默认**并行跑文件**，
而它们共享同一套开发网 —— 13 个文件 7 个失败，全是互踩）；4 处无界 `docker logs` 
（串行化后才暴露的顺序依赖）；`reset-bootstrap-roundtrip` 的销毁闸门不区分部署形态
（跨机形态下开启会重写不可复现的 Primary 创世，**废掉整套部署**）。
**共性**：这类缺陷**不会让任何被测功能变红**，只会让套件变成噪声或在某种顺序下炸掉。

### 另有一次真实硬件故障

ubuntu-1 网线故障，21% 丢包、TCP 连接时间出现 3s／7s／15s（SYN 重传退避），
而 **NIC 计数器全零**（帧完全没到达时不会被计数 —— 零错误与零丢包是两件事）。
换线后归零。诊断特征与排查次序记在 `docs/adr/0007-failure-domain-independence.md`。

值得记的是它**伪装成了测量噪声**：丢包期间 `devnet-status` 的瞬时 `unreachable` 与
高频探测里的零星样本，当时都被解释成"探测层抖动"—— 那是错的。
**"高频探测所以有抖动"是个太顺手的解释，用它之前先量一下丢包。**
