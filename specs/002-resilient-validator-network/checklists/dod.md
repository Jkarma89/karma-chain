## 四、回归：从克隆到可用链由 2 步变 3 步（SC-007 / FR-030）

**事实**：001 是 `git clone` + `scripts/devnet-start`（R-14 实测基准 2 步）。
002 是 `git clone` + `scripts/devnet-bootstrap` + `scripts/devnet-start` = **3 步**。

**为什么会这样**：建链制品（SubnetID／BlockchainID）提交在仓库里，但 Subnet 与 Blockchain 是
**P 链上的交易**，只存在于节点数据库里 —— 而数据卷不在 git 里。因此新克隆的仓库必须先建链一次。
这不是疏忽，是"制品是第二类事实"（[ADR-0009](../../../docs/adr/0009-chain-identity-as-second-class-fact.md)）
的直接后果。

**耗时口径是达标的**：建链约 80s（一次性）+ 首次启动 5–15s ≈ 95s ≤ 120s（基准 80s 的 1.5 倍）。
不达标的只有步骤计数。

**两条可选出路，需要项目负责人裁定**：

1. **让 `devnet-start` 在"制品在、P 链上没有那条链"时自动建链一次。** 恢复 2 步。
   代价：`devnet-start` 会在首次运行时调用建链镜像（含 CLI）。它仍不在**运行时**路径上
   （建链只发生一次），但会削弱"建链是一次显式的、有意识的动作"这一设计意图，
   并与当前那道给出 `stop → bootstrap → start` 指引的守卫冲突。
2. **接受 3 步，修订 SC-007。** 代价：一条成功判据被放宽；需在 spec 中说明理由
   （P 链状态无法进 git，这是架构性的，不是实现偷懒）。

**我的建议是第 2 条。** 第 1 条把两件性质不同的事（一次性建链 vs 日常启动）合进同一个命令，
换来的只是少敲一行；而"建链会在 P 链上创建 Subnet 与 Blockchain"这件事，值得让人显式触发一次。
但这是判据的修订，属于规格变更，不该由我单方面决定。

## 五、测试抓到的实现缺陷（第八条的实证）

这些不是"测试通过"，而是"测试**先失败**并因此改对了实现"——记录在此，因为它们是测试优先的实际收益：

| 测试 | 抓到的缺陷 |
|---|---|
| `topology-cli.test.mjs`（场景 G） | T-5 违规消息是英文，而契约规定中文且工具其余输出全是中文；顺带发现退出码 13 的判据靠匹配英文散文，文案一改就静默失效 |
| `reset-bootstrap-roundtrip.test.mjs`（T091） | `devnet-start` 在"卷已 reset 但制品仍在"时**等满 300 秒**才给一句无指向性的"未就绪"；`devnet-bootstrap` 误用退出码 11 |
| `crash-recovery-repeat.test.mjs`（50 轮） | **上一条的修复引入了假阳性**：新守卫在崩溃恢复时（P 链仍在引导）误判"链不存在"，把 US1 的恢复路径直接拦死。教训：打在正常路径上的诊断守卫必须**保守** —— 拿不准就放行 |
| `status-format.test.mjs`（T074） | `unreachable` 有两种含义且**离线语义相反**，只按状态名推断会虚报余量不足；摘要用观测行数做分母，少一行时会把缺失算成在线 |
| `bootstrap-idempotence.test.mjs` | 它自己**把误用写进了断言**（"端口/状态冲突应使用 11"），因此从未拦住那个误用 |
| `docs-drift.test.mjs` | 理由文件有三个键写在顶层，而渲染器只读 `.rationale` —— 说明根本没进文档，且它们本该更新的条目仍留着旧值 |

## 六、结论与建议

**阶段一（缺陷 A）可以认为完成**：崩溃后必须重置全链这条路径已消除，证据包括 **50 轮**重复
强制终止零丢失、超限安全停摆（回滚 0）、单节点数据丢失可局部重建、以及删掉全部 5 个验证者卷后
6 秒恢复。它与故障边界数量无关，因此**不受硬件缺口影响**。

**阶段二（缺陷 B）不能认为完成**：整域失效容忍需要 5 台独立物理机，当前 2 台。
运维方已裁定"按 5 台使用、接受当前可用性等级"，但那是接受**限制**，不是达成判据。

**建议的收尾顺序**：
1. 裁定 SC-007 的两条出路（本文第四节）
2. 补 SC-003 的 30 分钟观测窗口 —— 这项不需要新硬件，只需要时间
3. 硬件到位后做 T056（整域失效 e2e）与 SC-005／SC-008 的跨机形态验证
