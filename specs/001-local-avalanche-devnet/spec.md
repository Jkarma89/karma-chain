# Feature Specification: 本地可复现的 Avalanche L1 开发网络

**Feature Branch**: `001-local-avalanche-devnet`

**Created**: 2026-08-31

**Status**: Draft

**Input**: User description: "搭建本地可复现的 Avalanche L1 开发网络"

**Reference**: `doc/karmachain-spec-001-local-avalanche-L1.md`（参考规格；其可测试要点已合并进本文，实现层建议——目录结构、脚本名、容器编排——留待 `/speckit-plan`）

## 背景与目标

KarmaChain 的所有后续组件（智能合约、后端、索引器、前端、监控）都依赖一条可以在本地随时启动、状态可预期的 Avalanche L1 开发链。本功能交付的是这条链本身及其"可复现性"保证：任何开发者或 AI Agent 从版本库出发，不依赖任何人机器上的手工配置，都能得到一条参数完全一致、行为完全一致的本地 KarmaChain 开发网络。

本功能对应宪法第七条（基础设施可复现）、第十四条（区块链参数必须记录）、第十六条（协议配置唯一事实来源）的首次落地，也是第十五条"协议变更控制"流程所约束的第一个协议级产物（Genesis / Chain 配置）。

本功能建立的基础链路：

```text
Avalanche L1 → KarmaChain 网络 → 验证者 → 出块 → EVM → RPC
```

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一键启动本地开发链 (Priority: P1)

开发者克隆仓库后，按照文档执行一个启动动作，本地即出现一条运行中的 KarmaChain 开发网络：节点健康、持续出块、对外暴露一个 EVM 兼容的 JSON-RPC 访问点。开发者不需要理解 Avalanche 内部结构，也不需要手工修改任何配置。

**Why this priority**: 这是整个项目的地基。没有可运行的链，合约、后端、索引器都无法开发和验证；它单独存在即具备价值（可用于合约开发）。

**Independent Test**: 在一台仅安装了项目声明的前置依赖的干净机器上，克隆仓库 → 执行启动 → 使用任意标准 EVM 工具查询链 ID 与最新区块高度，两次查询区块高度递增即通过。

**Acceptance Scenarios**:

1. **Given** 干净的开发机已满足文档列出的前置依赖，**When** 开发者执行文档中的启动步骤，**Then** 在规定时间内（见 SC-001）网络进入"健康且出块"状态，并输出 RPC 访问地址、链 ID、预置账户信息。
2. **Given** 网络已启动，**When** 开发者用标准 EVM 工具（钱包、合约框架、JS 客户端任一）连接该 RPC，**Then** 工具能正确识别链 ID、读取区块与账户余额，无需任何自定义适配。
3. **Given** 网络已启动，**When** 开发者从预置开发账户向另一地址发送一笔原生代币转账，**Then** 交易在后续区块中被确认，可查询到交易回执，回执中的交易哈希、区块号、执行状态（成功）、Gas 用量、发送方、接收方均正确，且双方余额变化与转账金额及手续费一致。
4. **Given** 网络已启动，**When** 开发者执行停止步骤，**Then** 所有节点进程终止，不留下残留的后台进程或端口占用。

---

### User Story 2 - 任何人、任何时候重建得到相同的链 (Priority: P1)

两名开发者（或同一开发者在不同时间、不同机器上）分别从同一版本库状态启动网络，得到的链在协议层面完全一致：相同链 ID、相同创世状态、相同预置账户与余额、相同 Gas 规则、相同代币符号。开发者可以随时"重置"回创世状态。

**Why this priority**: "可复现"是本功能的核心承诺，也是宪法第七条的直接要求。没有它，团队将回到"我电脑上能跑"的状态，测试结果不可比对。

**Independent Test**: 在两个独立环境分别启动网络，对比创世区块哈希、链 ID、预置账户余额；再执行"重置"后重新启动，创世区块哈希应与之前一致。

**Acceptance Scenarios**:

1. **Given** 两个独立环境使用同一版本库提交，**When** 各自启动网络，**Then** 两条链的创世区块哈希、链 ID、原生代币符号、预置账户及余额完全相同。
2. **Given** 网络已运行并产生了若干交易，**When** 开发者执行"重置到创世"操作后重新启动，**Then** 链从创世状态重新开始，之前的交易与状态全部消失，创世区块哈希不变。
3. **Given** 网络已运行并产生了若干交易，**When** 开发者执行普通"停止 → 启动"（非重置），**Then** 链状态得到保留，区块高度从停止前的高度继续增长。
4. **Given** 版本库中的协议参数（如链 ID）被修改并提交，**When** 开发者重置并重新启动，**Then** 新链反映新的参数，且所有派生配置（文档、脚本输出、测试）与之一致，不存在任何一处仍显示旧值。

---

### User Story 3 - 协议参数有唯一出处且被完整记录 (Priority: P2)

架构师或审阅者能在版本库中的**一个**位置查到 KarmaChain 开发网络的全部协议参数（链 ID、网络 ID、原生代币名称/符号/精度、初始供应与分配、Gas 相关配置、区块参数、验证者配置、RPC 与 P2P 端口），并能确认所有其他地方（文档、启动脚本、测试、后续的后端/前端配置）都是从这个位置读取或生成的，而不是各自硬编码。

**Why this priority**: 宪法第十六条的强制要求；同时为后续 backend / frontend / deployment 功能提供依赖点。它可以独立于 P1 通过"审查 + 一致性检查"验证。

**Independent Test**: 审阅者阅读协议参数文件；运行"一致性检查"脚本或测试，验证运行中链的实际参数与文件声明完全一致，且仓库内不存在第二份互相矛盾的参数定义。

**Acceptance Scenarios**:

1. **Given** 版本库处于任意提交，**When** 审阅者查找链 ID，**Then** 只存在一个权威定义位置，其他所有出现该值的位置都可追溯为从该处生成或引用。
2. **Given** 网络已启动，**When** 运行参数一致性验证，**Then** 运行时链上报的链 ID、代币符号、创世账户余额与权威参数文件逐项一致。
3. **Given** 审阅者阅读协议参数文档，**When** 对照宪法第十四条清单（Chain ID、Native Token Symbol、Token Supply、Gas Configuration、Block Parameters、Validator Configuration、Genesis Configuration、Network ID），**Then** 每一项都有明确记录及其取值理由。

---

### User Story 4 - 自动化验证保证"启动成功"不是口头结论 (Priority: P2)

开发者（或 CI）可以运行一组自动化验证，对运行中的网络进行体检：节点健康、验证者健康、出块进行中、RPC 可用、链 ID 正确、预置账户余额正确、能成功发送并确认一笔交易、能成功部署并调用一个最小智能合约。验证以明确的通过/失败结论结束。"节点已启动"本身不构成通过。

**Why this priority**: 宪法第八条"先定义验证方法"和第十七条 DoD 的要求。它把 P1/P2 的验收场景固化为可重复执行的检查，也是后续所有功能的回归基线。

**Independent Test**: 对一条健康的网络运行验证 → 全部通过；对一条被人为停掉的网络运行验证 → 明确报告失败原因。

**Acceptance Scenarios**:

1. **Given** 网络健康运行，**When** 运行自动化验证，**Then** 所有检查项逐项通过并以成功状态退出，输出逐项结果与总结（如 "KarmaChain is READY"），摘要含链 ID、区块高度。
2. **Given** 网络未启动或节点不健康，**When** 运行自动化验证，**Then** 验证以失败状态退出，并指出是哪一项失败（如"RPC 不可达"、"5 秒内区块高度未增长"）以及失败所属类别（见 FR-030）。
3. **Given** 网络健康运行，**When** 验证流程部署一个最小 EVM 智能合约并调用其只读与写入方法，**Then** 部署交易被确认、写入调用改变了合约状态、只读调用返回预期值。
4. **Given** 网络健康运行，**When** 验证流程逐一调用 FR-012 列出的 JSON-RPC 方法，**Then** 每个方法返回符合以太坊 JSON-RPC 规范的结果；任何被记录为"不支持"的方法在验证中被明确标注而非静默跳过。

---

### User Story 5 - 可观测节点状态并诊断问题 (Priority: P3)

开发者在网络启动失败或行为异常时，能够查看结构化的节点日志，并通过健康检查确认每个节点的状态（是否健康、是否在出块、对等节点连接情况），而不需要猜测。失败信息足以区分是配置问题、节点问题、网络问题还是存储问题。

**Why this priority**: 宪法第九条要求核心组件可诊断。对本地开发网络而言这是提升开发体验与排障效率的保障，但不阻塞链本身的可用性。

**Independent Test**: 启动网络后查看日志与健康状态；人为制造一个故障（如端口冲突）后，日志与状态信息足以让开发者定位到原因。

**Acceptance Scenarios**:

1. **Given** 网络已启动，**When** 开发者查询节点健康状态，**Then** 能获得每个节点的健康结论、出块/同步状态、对等连接数（每个 L1 验证者至少与其余 4 个 L1 验证者建立连接，即 peers ≥ 4；网络共 7 个节点，精确期望值以实现期实测为准并记录在协议参数派生常量中）。
2. **Given** 启动时所需端口已被占用，**When** 开发者执行启动，**Then** 启动流程明确报告冲突的端口而非静默失败或无限等待。
3. **Given** 网络运行中，**When** 开发者查看日志，**Then** 日志可按节点区分，包含时间戳与级别，能观察到节点启动、验证者启动、对等连接、区块产生/导入、交易处理、RPC 请求、错误等关键事件。
4. **Given** 任意运行阶段，**When** 审阅者检查日志与启动输出，**Then** 其中不出现任何私钥、助记词、密码或其他秘密（预置开发账户密钥仅出现在被明确标记的密钥文件与文档中）。

---

### Edge Cases

- **端口被占用**：启动流程必须检测并明确报告，不得静默失败或挂起。
- **前置依赖缺失或版本不符**：启动流程在开始前检查并给出明确的缺失项提示。
- **重复启动**：网络已在运行时再次执行启动，应幂等（报告已运行）或明确拒绝，不得产生第二套冲突的节点。
- **非正常终止（断电、强制杀进程、宿主机重启）后再启动**：网络应能恢复到上次已持久化的状态，或明确提示需要重置；不得进入静默的损坏状态。
- **协议参数文件被修改但未重置**：启动流程应检测到现有链数据与当前参数不匹配，并提示开发者需要重置，而不是产生一条"半新半旧"的链。
- **磁盘空间不足**：节点应明确报错而非无声停止出块。
- **多次重置**：连续重置后创世区块哈希应始终一致（重置本身是确定性的）。
- **单个验证者宕机**：5 验证者网络中 1 个节点停止时，网络应继续出块并在健康检查中标出该节点不健康；**不确定**：Avalanche 共识下 5 节点可容忍的故障节点数需在规划阶段依官方文档核实，本规格不臆断。
- **时钟**：所有节点运行在同一宿主机上，不应因时钟漂移而停止出块；跨机部署不在本功能范围，文档需说明。
- **误连真实网络**：本地开发链的 Chain ID / Network ID 必须与 Avalanche 主网、测试网及 KarmaChain 未来主网不同，钱包不可能把本地链误认为真实链。

## Scope Boundaries

### In Scope

- 本地 KarmaChain Avalanche L1 网络的创建、启动、停止、重置、重建
- 协议参数唯一事实来源与 Genesis 版本化
- 5 个验证者节点组成的本地网络
- 标准 EVM JSON-RPC 访问与验证
- 原生代币（KarmaCoin / KARMA）的创世分配、余额查询、基础转账
- 一次真实 EVM 交易（转账）与一次最小合约部署/调用的端到端验证
- 自动化验证、健康检查、日志与故障分类
- 开发者文档与架构决策记录

### Out of Scope（后续独立功能）

- 生产 / Staging / 云端部署、公网验证者
- 钱包 UI、MetaMask 集成 UI
- 区块浏览器、交易索引系统
- ERC-20 / NFT / 复杂智能合约、DeFi、DAO、Oracle、跨链
- Staking 业务系统、Token 市场 / 交易所 / UI
- 后端业务 API、前端 DApp、用户注册 / 登录 / 数据库

## Requirements *(mandatory)*

### Functional Requirements

**启动 / 停止 / 重置**

- **FR-001**: 系统 MUST 提供一个从版本库出发、单一入口的启动动作，使开发者在完成文档声明的前置依赖后无需任何手工配置即可启动本地 KarmaChain 开发网络。该动作 MUST 覆盖完整流水线：生成配置 → 生成 Genesis → 初始化节点 → 启动节点与验证者 → 等待网络就绪 → 输出访问信息。
- **FR-002**: 若任何一步在当前阶段无法自动化而必须手工执行，MUST 在文档中记录该步骤、原因及后续自动化计划。
- **FR-003**: 系统 MUST 提供对应的停止动作，停止后不留下残余进程与端口占用。
- **FR-004**: 系统 MUST 提供"重置到创世"动作，清除全部链数据并使下次启动从创世状态开始。
- **FR-005**: 普通停止后再次启动 MUST 保留链状态并从上次高度继续。
- **FR-006**: 启动动作 MUST 是幂等的或在网络已运行时明确拒绝，不得创建第二套冲突节点。
- **FR-007**: 启动动作 MUST 在启动前检查前置依赖与端口可用性，缺失或冲突时给出明确、可操作的错误信息。
- **FR-008**: 启动完成后系统 MUST 输出开发者立刻需要的信息：RPC 访问地址、链 ID、原生代币符号、预置开发账户地址及其余额。

**网络形态**

- **FR-009**: 本地开发网络 MUST 以 Avalanche L1（Subnet）形式运行，而不是直接复用 Avalanche 主网/测试网的 C-Chain。
- **FR-010**: 本地开发网络 MUST 由 **5 个验证者节点**组成，全部运行在同一宿主机上；每个验证者 MUST 能启动、加入网络、参与共识、持续同步区块，并与其余节点建立对等连接。
- **FR-011**: 网络 MUST 持续出块（或在有交易时出块，视所选出块模式而定，须在协议参数中明确记录），并可通过标准手段观测到区块高度持续增长（N → N+1 → N+2 …）。

**EVM 兼容性（宪法第三条）**

- **FR-012**: 网络 MUST 暴露标准的 Ethereum JSON-RPC 访问点，至少验证以下方法可用且行为符合规范：`eth_chainId`、`eth_blockNumber`、`eth_getBlockByNumber`、`eth_getBlockByHash`、`eth_getBalance`、`eth_getTransactionCount`、`eth_sendRawTransaction`、`eth_getTransactionByHash`、`eth_getTransactionReceipt`、`eth_call`。实际支持情况 MUST 以锁定版本的 Avalanche L1 / EVM 实现为准，不得臆测；若某方法不被支持，MUST 在文档和自动化验证中明确标注。
- **FR-013**: 主流 EVM 工具（钱包、合约开发框架、JS/TS 客户端）MUST 无需自定义适配即可连接、读取、发送交易、部署与调用合约。
- **FR-014**: 网络 MUST 使用标准 EVM 语义执行 Solidity 合约，支持账户、以太坊式原生资产模型、Nonce、Gas、交易、合约部署与调用、事件/日志、区块、回执；任何与标准行为的偏离 MUST 在协议参数文档中显式记录并说明原因。本功能默认不引入任何偏离。
- **FR-015**: 交易回执 MUST 可查询，且至少包含并正确反映：交易哈希、区块号、执行状态、Gas 用量、发送方、接收方；对应的状态变化（余额）MUST 可通过 RPC 核对。

**协议参数与唯一事实来源（宪法第十四、十六条）**

- **FR-016**: 版本库 MUST 包含唯一一个权威的协议参数定义，至少涵盖：Chain ID、Network ID、原生代币名称/符号/精度、初始供应量与分配、Gas 配置、区块参数、验证者配置、Genesis 配置、RPC 与 P2P 端口。
- **FR-017**: 创世文件、启动脚本输出、文档、自动化验证以及后续任何组件配置中出现的协议参数 MUST 从该权威定义生成或读取，不得独立硬编码。
- **FR-018**: 本地开发网络的链身份参数 MUST 为：**Chain ID = 20189**（本地开发网专用）；**20188 预留给 KarmaChain 未来主网**，本地开发网 MUST NOT 使用 20188；原生代币 **名称 KarmaCoin、符号 KARMA、精度 18**。两个 Chain ID 已于 2026-08-31 核实在公开链 ID 注册表（ethereum-lists/chains）中均未被占用；正式对外发布前 MUST 再次核实并提交注册。
- **FR-019**: 为方便开发而临时更改 Chain ID 属于协议变更，MUST 按宪法第十五条流程处理，MUST NOT 随意进行。
- **FR-020**: 每一项协议参数 MUST 记录其取值及选择理由（宪法第十四条），并且文档记录的值 MUST 与实际运行网络一致，可由自动化验证核对。
- **FR-021**: 系统 MUST 在启动时检测已存在的链数据是否与当前协议参数一致，不一致时拒绝启动并提示重置。

**开发账户与安全（宪法第四条）**

- **FR-022**: 创世状态 MUST 包含若干预置并已注资的开发账户，供本地开发与测试使用。
- **FR-023**: 预置开发账户及开发验证者的密钥 MUST 被明确标记为 "DEVELOPMENT ONLY — 仅供本地开发、公开已知、绝不可用于生产"，且这一警告 MUST 出现在密钥所在文件、文档与启动输出中。本项依据宪法第四条 v1.1.0"公开已知的本地开发密钥"例外条款执行，须同时满足其全部四个条件。
- **FR-024**: 版本库中除上述明确标记的本地开发用密钥外，MUST NOT 包含任何真实私钥、助记词、验证者密钥或其他秘密；本地网络运行时生成的节点数据 MUST 位于版本控制忽略范围内。
- **FR-025**: 本功能交付的 Genesis 与配置 MUST 明确标记为开发环境专用，并与未来的测试 / Staging / 生产配置在物理位置上分离；生产环境的 Genesis / 密钥 / 验证者配置不在本功能范围内，文档 MUST 明确禁止复用（宪法第四条）。
- **FR-026**: 节点日志与启动输出 MUST NOT 泄露私钥、助记词、密码或其他秘密。

**验证（宪法第八条）**

- **FR-027**: 系统 MUST 提供可重复执行的自动化验证，至少按以下顺序覆盖：节点运行 → 验证者运行且健康 → RPC 可用 → 链 ID 与代币符号与权威参数一致 → 区块高度持续增长 → 预置账户余额与创世一致 → 一笔原生代币转账被确认且回执字段正确（FR-015）→ 一个最小智能合约被部署且读写调用成功 → FR-012 所列 RPC 方法逐一验证。
- **FR-028**: 自动化验证 MUST 逐项输出通过/失败结果，并以明确的总体成功/失败状态结束；失败时指出失败项及其类别（FR-030）。
- **FR-029**: 上述验证 MUST 可在无人交互的情况下运行，以便作为后续所有功能的回归基线；"节点已启动"单独不得视为通过。

**可观测性与故障处理（宪法第九条）**

- **FR-030**: 网络启动失败或验证失败时，系统 MUST 至少能区分以下故障类别之一：Genesis 错误、配置错误、节点错误、验证者错误、P2P 错误、RPC 错误、EVM 错误、交易错误、存储错误；不得只给出"网络失败"之类无进一步信息的结论。
- **FR-031**: 每个节点的日志 MUST 可被开发者获取，按节点区分，包含时间戳与级别，并能观察到以下关键事件：节点启动、验证者启动、网络连接、对等节点连接、区块产生、区块导入、交易处理、RPC 请求、错误。
- **FR-032**: 系统 MUST 提供获取每个节点健康状态（健康结论、出块/同步状态、对等连接数）的方式。

**文档（宪法第七、十四条）**

- **FR-033**: 版本库 MUST 包含开发者文档，涵盖：前置依赖及版本要求、启动/停止/重置步骤、如何连接常见 EVM 工具、预置账户、协议参数说明与理由、RPC 方法支持情况、常见故障排查（按 FR-030 类别组织）。
- **FR-034**: 文档 MUST 记录本次的架构决策（为何 Avalanche L1、为何 EVM、5 验证者拓扑、Chain ID 20189/20188 的选择、出块模式选择），格式满足宪法第十四条"决定了什么 / 为什么 / 替代方案 / 影响 / 迁移"。

### Key Entities

- **协议参数（Protocol Config）**：KarmaChain 开发网络全部共识相关参数的唯一权威定义。属性：Chain ID（20189）、Network ID、原生代币（KarmaCoin / KARMA / 18）、初始供应与分配表、Gas 配置、区块参数、验证者配置（5 节点）、出块模式、RPC 与 P2P 端口。其他所有实体均由它派生。
- **创世配置（Genesis）**：由协议参数派生的链初始状态描述，决定创世区块哈希。相同协议参数 ⇒ 相同创世哈希。
- **验证者节点（Validator Node）**：参与共识、出块的本地进程/容器，共 5 个。属性：节点标识、健康状态、对等连接数、RPC 端点、日志、数据目录（不入版本库）。
- **预置开发账户（Dev Account）**：创世时注资、密钥公开、仅供本地使用的账户。属性：地址、初始余额、"DEVELOPMENT ONLY" 标记。
- **链数据（Chain Data）**：节点运行产生的持久化状态；停止后保留，重置时清除；与协议参数存在一致性约束。
- **验证报告（Verification Report）**：一次自动化验证的结果。属性：时间、各检查项及结论、失败类别、总体通过/失败。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在满足前置依赖的开发机上，从执行启动到 5 节点网络"全部健康且出块"的时间不超过 5 分钟（首次启动含依赖拉取可放宽到 15 分钟）。
- **SC-002**: 两个独立环境从同一版本库提交启动，创世区块哈希、链 ID、代币符号、预置账户余额 100% 一致。
- **SC-003**: 连续 10 次"重置 → 启动"得到的创世区块哈希完全一致。
- **SC-004**: 至少 3 种主流 EVM 工具（钱包、合约开发框架、JS/TS 客户端各取一种）无需任何自定义适配即可连接网络并完成"读取余额 → 发送交易 → 确认"流程。
- **SC-005**: 自动化验证全部检查项在健康网络上 100% 通过，且整套验证在 3 分钟内完成。
- **SC-006**: 一笔普通原生代币转账从提交到被确认不超过 10 秒。
- **SC-007**: 版本库中链 ID 等协议参数只存在一个权威定义；对全库进行字面值搜索，其他出现处均可追溯为生成/引用（0 处独立硬编码）。
- **SC-008**: 新加入的开发者仅依靠文档，在不向他人求助的情况下首次成功启动网络并部署一个合约（以团队内至少 2 人试用，成功率 100%）。
- **SC-009**: 版本库中不存在任何非"明确标记为本地开发专用"的私钥、助记词或验证者密钥（秘密扫描 0 命中）；节点日志中秘密扫描 0 命中。
- **SC-010**: FR-012 所列 10 个 JSON-RPC 方法中，每一个要么通过自动化验证，要么在文档中被明确标注为不支持及原因（0 个"未知状态"）。
- **SC-011**: 人为制造的每一类可复现故障（端口占用、依赖缺失、参数与链数据不一致、单节点停止），验证/启动输出都能归入 FR-030 的正确类别（分类准确率 100%）。

## Assumptions

- **范围边界**：见 Scope Boundaries。本功能仅需保证为后续组件预留稳定的 RPC 端点、预置账户与协议参数出处。
- **运行环境**：目标是在 Windows、macOS、Linux 三类开发机上均可运行；依宪法第七条推荐，假定通过容器化方式实现跨平台一致性，开发者只需安装文档声明的少量前置依赖。5 个验证者全部运行在同一台宿主机上，跨机部署不在范围内。5 节点对内存/CPU 的实际要求在规划阶段测定并写入文档的前置条件。
- **Avalanche 网络形态**：本地网络包含一个本地 Primary Network（P-Chain/C-Chain/X-Chain 本地实例）与一条 KarmaChain L1（Subnet-EVM 类型的 EVM 链）。开发者日常只与 KarmaChain L1 的 RPC 交互；Primary Network 的存在对开发者透明。
- **链身份决策记录**：本地开发网 Chain ID 20189，未来主网预留 20188，二者分离是为了从第一天隔离本地/生产链身份、避免钱包误连与 Genesis 混用（宪法第四条）。2026-08-31 核实：ethereum-lists/chains（2739 条记录）中 20188、20189 均未注册；注意相邻的 20261 已被占用，说明该区段并非完全空闲，正式发布前需再次核实并注册。Network ID 的取值在规划阶段依 Avalanche 本地网络的约定确定并记录。
- **开发账户密钥**：采用"公开已知、仓库内明文、显著警告"的做法（与主流 EVM 本地开发工具的惯例一致）；宪法第四条的"禁止提交私钥"针对真实秘密。本假设需在规划阶段的安全考虑中记录。生产环境绝不使用这些账户。
- **出块模式**：默认假定网络持续出块或在有交易时快速出块，具体模式在 `/speckit-plan` 阶段依据 Avalanche L1 的实际能力确定，并记录在协议参数中。**不确定**：Avalanche Subnet-EVM 的确切出块行为与 5 节点容错阈值需在规划阶段查阅锁定版本的官方文档核实，本规格不臆断（宪法第十二条）。
- **协议参数格式**：权威定义采用人可读、机器可解析的单一文件，具体格式在规划阶段决定。
- **配置分环境**：开发/测试/Staging/生产配置在物理位置上分离（FR-025）；具体目录布局属于规划阶段决定。
- **版本锁定**：Avalanche 节点软件与 L1 虚拟机的版本 MUST 被锁定在版本库中，作为可复现性的一部分；升级视为协议变更（宪法第十五条）。工具选型优先使用 Avalanche 官方支持的 L1 创建、节点运行与 EVM 组件，以锁定版本的官方文档和源码为准，不依据旧版教程推测行为。
- **安全考虑（宪法第四、十二条）**：本功能涉及 Genesis、Chain ID、代币经济、验证者配置，属于协议级产物。虽然是开发环境专用，仍需在规划阶段记录：① 开发密钥泄漏边界（仅本地）；② 本地网络与真实网络的隔离（Chain ID 20189 ≠ 20188，Network ID 与 Avalanche 主网/测试网不同）；③ 生产 Genesis 与本地 Genesis 的严格分离机制；④ 日志不泄密的实现方式。
- **后续依赖与路线图**：参考规格建议的后续顺序为 002 验证者与网络 → 003 原生代币 → 004 EVM RPC → 005 钱包与转账 → 006 智能合约 → 007 索引器 → 008 区块浏览器 → 009 后端 → 010 前端 DApp。由于本功能已覆盖基础转账与 RPC 验证，002–004 预计可合并或大幅缩减；智能合约、索引器、后端功能将直接依赖本功能提供的 RPC 端点、预置账户与协议参数出处。
