# ADR-0011：代理的健康位只回答代理自己

**状态**：已采纳（2026-09-11）
**背景特性**：[004 RPC 入口可用性修复与「恢复能力」呈现](../../specs/004-rpc-entry-recovery-visibility/spec.md)
**取代 / 相关**：[ADR-0010 面板作为链的只读旁观者](0010-readonly-observability-dashboard.md)、[ADR-0007 故障边界独立性](0007-failure-domain-independence.md)

## 决定了什么

RPC 代理容器的 Docker healthcheck 探测一个**由 nginx 自己应答**的位置
（`location = /_alive`，`return 200`），**不 `proxy_pass`**、不接触任何上游节点。

它回答的问题是：**这个代理容器本身有没有在正常工作** —— nginx 进程活着、
配置解析通过、端口在监听。

它**不回答**「链能不能用」。那由面板（003）与 `devnet-verify` 回答。

「面向客户端的 RPC 路径能否被正确改写并转发」也**不由它回答** ——
那是生成物的**静态属性**，由 `npm run render:check` 的漂移核对与
`tests/unit/rpc-proxy-failover.test.mjs` 守着（规格 FR-034）。

## 为什么 —— 一个缺陷的完整成因链

2026-09-10，003 面板验收当天：两个 Primary 全停时 RPC 入口**间歇性返回 502**，
而五个 L1 验证者在各自端口上全部 200、高度一致、直连提交的交易确认于区块 835
（4108 ms）。**链好着，门坏了。**

| # | 环节 | 证据 |
|---|---|---|
| 1 | 两个 Primary 停 → 五个 L1 自报的**综合**健康位 `/ext/health` 全部 **503**（它含 P 链可达性） | 逐台直连实测 |
| 2 | 代理容器的 healthcheck 是 `wget … http://127.0.0.1:<port>/ext/health` —— **经由代理自己**打到上游 | nginx 访问日志里 User-Agent 为 `Wget`、client 为 `127.0.0.1` |
| 3 | `proxy_next_upstream … http_503` 把上游的 503 应答**计为一次失败** | 生成的 `rpc-proxy.conf` |
| 4 | `max_fails=1 fail_timeout=60s` —— 一次失败就关该上游 60 秒 | 同上 |
| 5 | `proxy_next_upstream_tries 5` 让**同一个** healthcheck 依次试完五个上游 → **一次探测毒遍全部** | 日志里一条请求连续四行 `upstream server temporarily disabled` |
| 6 | healthcheck 间隔 **10 秒 < 60 秒**惩罚期 → 惩罚期**永不排空** | compose 的 `interval: 10s` |
| 7 | 真实客户端流量随之 `no live upstreams` → **502** | 日志里 `POST … 502`，以及偶发漏过的 `POST … 200` 窗口 |

### 这是同一个陷阱下沉了一层

003 的 FR-013 在**面板**里禁掉了综合健康位（`tests/unit/dashboard-boundaries.test.mjs`
静态禁止那个字符串）；002 的**节点** healthcheck（`docker/node/healthcheck.sh`）
当年也刻意避开了它并把理由写进了 `contracts/node-runtime.md`。

而 002 的**代理** healthcheck 用的正是它。**一个地方记住了教训，另一个地方没有。**

后果是 002「两个 Primary 全停，L1 仍可服务」这个结论
**在节点层面成立、在它自己文档写明的入口层面不成立** ——
而绝大多数使用者只有入口这一条路。

### 一个此前没被注意到的放大器

`upstream` 块里有 `zone karmachain_rpc 64k;`，它让失败计数**在所有 worker 之间共享**
（002 实测 `nginx:alpine` 默认起了 **18 个 worker**）。

`zone` 本身是 002 为**另一个**问题加的**正确**修复：不加它，失败计数每个 worker 各记一份，
整域缺席时几乎每次请求都命中一个"还不知道那台已死"的 worker，重新付 2 秒连接超时。

但它同时把本缺陷从"每个 worker 各自被毒"放大成**一次探测毒遍全体 worker 的共享状态**。

> **一个正确的修复放大了另一个缺陷。** 记下来是因为它说明
> "每个改动单独都对"不等于"合起来也对" —— 而合起来的行为没有任何单元测试覆盖。

## 考虑过的替代方案

这四条都被认真考虑过又否决了，写下来是为了让日后想改的人知道代价在哪。

### 1. 为何**不**用 POST `eth_chainId` 经 RPC 路径探测

它能顺便覆盖「改写与转发是否正确」，听起来更有价值。否决理由三条：

- 它**仍然接触上游**，只是把"必然制造失败"换成"可能参与制造失败"。
  而本缺陷的病因恰恰是探测在制造失败 —— 换个剂量不叫治好。
- **会引入一种新的假红**：所有 L1 引导中时该路径返回 404（链还没注册），
  healthcheck 变红，而代理完全正常。跨机分批启动时引导常常超过 `start_period: 60s`。
- 依赖 busybox `wget --post-data`，未经验证 —— 而新增一个未验证的依赖去换一个
  我们并不需要的判断范围，方向是错的。

**这一条与 FR-003 在结构上冲突**：要验证转发就必须接触上游，接触上游就可能参与失败计数。
两条要求在同一个探测里无法同时满足 —— 所以拆到两个机制里（见"决定了什么"第四段）。

### 2. 为何**不**从 `proxy_next_upstream` 里删掉 `http_503`

删掉它，503 就不再被计为上游失败，本缺陷也随之消失。但那会改变**真实流量**的
故障转移语义（一个 502/503 不再换下一个上游）。

**为了修探测的问题去动业务路径，方向是错的。**

### 3. 为何**不**把 healthcheck 间隔拉长到超过 `fail_timeout`

那只是把中毒频率降低，病因没去掉 —— 惩罚期仍会被周期性续上，只是稀疏一些。
而且会让容器健康位的延迟变差。

### 4. 为何**不**干脆删掉代理的 healthcheck

那就再也不知道代理死了。**一个不会变红的守卫比没有守卫更坏，而没有守卫也是坏的。**

## 一并决定：三个故障转移参数一律不动

`max_fails=1` / `fail_timeout=60s` / `proxy_next_upstream` / `zone` / `ip_hash` /
三项超时 —— **一个字符都不改**。

它们是 002 在 **2026-09-09 实测后**专门定下的，推导写在
`tools/protocol/render-rpc-proxy.mjs` 的注释里：

- `max_fails=2 fail_timeout=10s` 在**低频请求下等于没生效**：请求间隔一旦超过
  `fail_timeout`，窗口内只累积到 1 次失败，永远到不了 2 次 —— 死节点因此从不被标记，
  每个请求都要重新付一遍连接超时。**5 次测量 5 次都付了。**
- `fail_timeout` 15s → 60s：反复去探一个持续死着的后端没有收益；而 `ip_hash`
  在后端被标记/恢复时会重新分配，每分钟 4 次重探 = 每分钟 4 次机会打断
  "读到自己刚写的"那份客户端亲和性。

> **看到 `max_fails=1 fail_timeout=60s` 的本能反应是"太激进、放宽一点"。**
> 但当前的 502 不是这些参数的错，是探测在制造失败。**先去病因，再谈剂量。**
> 放宽它们会把 002 已经解决的另一个问题放回来 ——
> 而改一个自己没有量过的参数，是在用别人量过的结论换自己的直觉。

`tests/unit/rpc-proxy-failover.test.mjs` 里有一组断言专门守这件事
（"什么都没改"也需要守卫）。要调的正确做法是：**先删掉对应断言并写明新的实测依据**，
而不是让断言跟着实现一起改。

## 影响

**改动面**：两个生成器各几行（`render-rpc-proxy.mjs` 加一个 location 并导出
`PROXY_PROBE_PATH`；`render-compose.mjs` import 它）。生成物只变 8 个文件：
两份 `rpc-proxy.conf` 各 +9 行、六份 compose 各 1 行。

**不需要重置链**：`blockchain/protocol.json` 与 `configVersion` **逐字节未变**
（healthcheck 取值硬编码在生成器里，不在协议文件里），创世哈希不变，
节点标志不变 —— 不触发出生证明（stamp）守卫。

**节点容器不动**：`docker compose -f <形态> up -d --no-deps --force-recreate rpc`
只重建代理。2026-09-11 用 `--dry-run` 确认过：指定服务名时 `depends_on` 的节点
只被标为 `Running` 而不重建；win-1 实测重建前后节点的 `Created` / `StartedAt`
逐字符相同。

**一个会被误解的行为**：全部上游不可服务时，代理健康位**仍然是 healthy**。
这是特性不是缺陷 —— 代理确实在正常工作。契约里为此专门立了一条**反向断言**
（C-5 / V-02b）：它和"会变红"同等重要，因为本决定的实质是**让判据少看一些东西**，
而少看东西的判据天生更容易变成永远绿。

## 迁移

逐台执行（五台都要做，一台不做那台的入口行为就还是旧的），步骤见
`docs/devnet.md` **§9.3.1**。要点两条：

1. **渲染只在一台机器上做一次**，生成物进 git ——
   三台 Ubuntu 宿主不装 Node，在那里跑 `npm run render` 会得到 `Command 'npm' not found`。
2. 必须**重建**容器而不是 `restart` / `nginx -s reload`：单文件 bind mount 绑的是 inode，
   `git pull` 是原子替换，`reload` 会打印 `signal process started` 看着像成功，
   **重载的是旧配置**。这个坑**只在 Linux 宿主上存在**（Docker Desktop 按路径解析）——
   "在 Windows 上开发、在 Linux 上部署"正是最坏的组合。

## 验证

2026-09-11 五台机器实测（`specs/004-.../research.md` 的 V-03）：
两个 Primary 全停的 **554 秒**窗口内，五个边界的入口各 **10 笔真实交易全部确认**、
各 20 次读请求，**5xx 零次**。

**这是一次差分，不只是一次通过** —— 同一场景 2026-09-10 产生的是间歇性 502，
而条件没有任何变化：窗口期间五个 L1 自报的综合健康位**仍然全部 503**。

| | 旧探测 | 新探测 |
|---|---|---|
| 五个 L1 的 `/ext/health` | 503 | **503（照样）** |
| 代理日志 `GET /ext/health` | 每 10 秒一条 | **0 次** |
| `no live upstreams` | 多次 | **0 次** |
| `upstream … temporarily disabled` | 一条请求连四行 | **0 次** |
| 502 应答 | 有 | **0 次** |
| 从入口发交易 | 发不出去 | **50/50 确认** |

唯一的变化是**探测不再接触上游**。
