# ADR-0006：Windows 故障边界不做开机自启，接受人工恢复

**状态**：已接受 · **日期**：2026-09-07 · **决策者**：项目负责人 · **相关**：宪法第七/十二条 · **来源**：功能 002 研究 R-11、V-09、T063

## 决定了什么

两台 Windows 机器（`win-1`、`win-2`）上的节点**不做开机自启**。宿主重启后由人登录并手动启动 Docker，
节点随之由容器重启策略（`restart: unless-stopped`）恢复。

Linux 边界不受此决定影响：那里 `docker.service` 是开机自启的系统服务，容器随之自动回来。

## 为什么不是别的方案

R-11 列了三个候选，V-09 实测后可选范围只剩两个 —— **候选 2 不是取舍问题，是技术上不可能**。

### 候选 2（WSL2 内跑 Docker Engine + 开机计划任务）已被硬证据否决

开机触发的计划任务运行在 LOCAL SYSTEM 上下文。实测该上下文下启动 WSL：

```
whoami=nt authority\system
exitcode=-1
错误代码: Wsl/WSL_E_LOCAL_SYSTEM_NOT_SUPPORTED
```

Windows **显式拒绝**从 SYSTEM 账户启动 WSL。同一脚本在交互用户下 `exitcode=0`、输出 `wsl-ok`，对照成立。
Docker Desktop 的引擎住在 `docker-desktop` 这个 WSL2 发行版里，即便换成 WSL 内的原生 Docker Engine
也一样要先有 WSL —— 所以"绕开会话依赖"这条路在 Windows 上走不通。

> 取证中的一个混淆项值得记下：第一次测试用 `powershell -File <未签名 .ps1>`，得到 `LastTaskResult=1`
> 且标记文件未生成，看起来像 WSL 失败。实际是 `LocalMachine` 执行策略为 `RemoteSigned` 挡下了脚本
> （交互会话因 `Process=Bypass` 不受影响）。改用 `-EncodedCommand` 后任务本身成功执行，才拿到真正的
> WSL 错误码。**"任务失败"与"任务里的命令失败"必须分开验证**，否则会把结论归到错误的原因上。

### 与另外两个方案的比较

| 方案 | 宿主重启后 | 代价 | 采纳 |
|---|---|---|---|
| 候选 1：开启宿主自动登录 | 自动回来 | 留下一个**已解锁的交互桌面** | 否 |
| 第四种（V-09 期间发现，R-11 未列）：计划任务以该用户身份运行 + 勾选"不管用户是否登录都要运行" | 自动回来 | 任务凭据里保存该账户口令，但**不留解锁桌面** | 否 |
| **候选 3：接受人工恢复** | 需人工登录并启动 Docker | 恢复时间取决于人 | **是** |

第四种方案跑在该用户的**批处理登录会话**里而非 SYSTEM，因此不撞上 `WSL_E_LOCAL_SYSTEM_NOT_SUPPORTED`；
它比自动登录克制。**未实测** —— 验证需要账户口令，属运维方自行执行的范畴。

选候选 3 的理由是**它不需要用宿主安全性去换恢复速度**。前两个方案都要在机器上留下一份可被滥用的凭据
（解锁的桌面，或任务凭据里的口令），而收益只是省掉一次登录。开发网没有随时可用的承诺，
这个交换不划算。

## 后果（必须写清楚，因为它比看起来严重）

**恢复时间取决于人，且两台 Windows 各自门控着不止一个节点** —— 因为它们同时是虚拟化宿主
（见 ADR-0007）：

| 宿主 | 登录后需手动做的事 | 随之恢复的节点 |
|---|---|---|
| `win-1` | ① 启动 Docker Desktop ② 启动 VMware Workstation 并开机 U22Node1、U22Node2 | `l1-1`；以及虚拟机内自动回来的 `l1-3`、`l1-4`、`primary-1`、`primary-2` |
| `win-2` | ① 启动 Docker Desktop ② 启动 VMware Workstation 并开机 U22Node3 | `l1-2`；以及虚拟机内自动回来的 `l1-5` |

虚拟机**内部**不需要人工介入：Ubuntu 里 `docker.service` 开机自启，容器由 `unless-stopped` 恢复。
人工步骤只在两台 Windows 宿主上。

由此：

- **停电后全链恢复需要有人登录 win-1**（它门控 3 个验证者 + 2 个 Primary）。在此之前链会停摆。
- 这不是新引入的风险，而是把 ADR-0007 记录的"2 个有效故障边界"这一事实在运维层面的体现。
- **链的正确性不依赖它**：停摆是安全的（V-05 实测：不分叉、区块零回滚、恢复后自动继续），
  数据也不会丢（US1 实测：节点各自从数据卷恢复，无需快照、无需重置）。
  也就是说人工步骤影响的是**可用性**，不是安全性或数据完整性。

### 补偿手段

- **US6 的可观测性**：`devnet-status` 须能把"边界缺席"与"节点故障"区分开（T076），
  这样运维一眼能看出"该去登录哪台机器"而不是去排查节点。这是本决定的必要配套，不可省略。
- **重启策略选 `unless-stopped` 而非 `always`**：两者在 Docker 守护进程启动时都会拉起容器，
  差别在于操作者此前显式跑过 `devnet-stop` 的情况 —— `always` 会把它们又拉起来，
  `unless-stopped` 尊重那次显式停止。后者才是正确语义。

## 迁移

若人工恢复在实践中变得难以接受，**优先考虑上表的"第四种方案"**而不是自动登录：
同样拿到自动恢复，但不留解锁桌面。落地步骤（在该 Windows 宿主上，以管理员身份）：

1. 建计划任务：触发器"启动时"，操作为启动 Docker Desktop（必要时再启动 VMware 并开机对应虚拟机），
   安全选项选"使用以下用户账户运行"并勾选"不管用户是否登录都要运行"。
2. 先在**登录状态下**手动运行一次该任务，确认 WSL 能起（即不报
   `WSL_E_LOCAL_SYSTEM_NOT_SUPPORTED` —— 确认它跑的是用户身份而不是 SYSTEM）。
3. 真正重启一次宿主验证，并把结果回写本 ADR 与 research.md 的 V-09。

反过来，若将来 Windows 支持以服务方式运行容器运行时（届时候选 2 的障碍消失），
应当优先切回那条路 —— 它不需要任何存储的凭据。

## 影响

- 两台 Windows 上不新增任何自启配置；不启用自动登录；不创建持久计划任务
- `docs/devnet.md` 的跨机部署章节须写明上表的人工恢复步骤（T066）
- `tools/inspect/node-status.mjs` 必须能区分"边界缺席"与"节点故障"（T076）—— 本决定的必要配套
- research.md 的 V-09 记录候选 2 的否决证据与本次选型
