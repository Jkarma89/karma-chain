# ADR-0005：KarmaChain 采用无许可（permissionless）模型

**状态**：已接受 · **日期**：2026-09-03 · **决策者**：项目负责人 · **相关**：宪法第一/二/四/六/十五条

## 决定了什么

KarmaChain 的定位是**开放的公链生态**：任何人都可以在链上部署智能合约、发送交易，无需事先获得许可。

具体表现为**不启用** Subnet-EVM 的许可类预编译：

| 预编译 | 状态 | 含义 |
|---|---|---|
| `contractDeployerAllowListConfig` | **不启用** | 任何账户都能部署合约 |
| `txAllowListConfig` | **不启用** | 任何账户都能发送交易 |
| `contractNativeMinterConfig` | **不启用** | 无人能凭空增发原生代币（含项目方） |
| `feeManagerConfig` | **不启用** | 费率参数不可在链上动态改动，只能走协议变更 |
| `rewardManagerConfig` | **不启用** | 手续费销毁，不可在链上改为分配给他人 |

创世中唯一启用的是 `warpConfig`——它是 L1 与 Avalanche P-Chain 通信（验证者管理）的必需组件，不是权限控制。

这一配置**当前已生效**（`blockchain/genesis/karmachain.genesis.json`），本 ADR 是把既有状态确认为有意识的架构选择，而非默认值的偶然结果。

## 为什么

1. **开放是生态繁荣的前提**。许可制会把"谁能创新"的决定权交给项目方，从根本上限制第三方开发者、DeFi 协议、工具作者的参与意愿。公链的价值来自参与者数量，而不是控制力。
2. **与宪法第一条一致**。"链是所有共识相关状态的最终权威数据源"——如果部署权由某个白名单管理员掌握，那这个管理员就成了事实上的权威，与去信任化的初衷冲突。
3. **恶意合约伤害不了链本身**。EVM 沙箱保证：合约无法窃取他人资产（转账需私钥签名）、无法死循环卡链（gas 上限）、无法篡改其他合约存储、无法修改共识规则或增发原生代币。风险集中在"与恶意合约交互的用户"，属于社会工程学问题。
4. **防御手段本就在链下**。合约审计、前端代币白名单、浏览器源码验证与诈骗标记、钱包交易模拟与授权提示、索引器异常监控——这些全部是链下系统，正对应宪法第二条"需要去信任化的放链上，普通业务逻辑放链下"。用链层许可去解决链下问题是错配。
5. **保留可逆性**。真需要收紧时，启用白名单是一次协议变更（见"迁移"），而从许可制走向开放却会遭遇既得利益与信任问题——**先开放后收紧比先收紧后开放容易**。

## 考虑过的替代方案

| 方案 | 否决理由 |
|---|---|
| **许可部署**（启用 `contractDeployerAllowListConfig`） | 项目方成为创新的守门人；与开放生态定位冲突；且开发阶段每个开发者都要加白，增加摩擦 |
| **许可交易**（启用 `txAllowListConfig`） | 更严格，适合 KYC/联盟链场景，与本项目定位不符 |
| **上线初期许可、成熟后开放** | 看似稳妥，但"何时开放"缺乏客观标准，实践中容易长期停留在许可态；且早期生态参与者会因不确定性而观望 |
| **启用 `feeManagerConfig` 以便动态调费** | 把 Gas 规则的修改权放到链上某个地址手里，等于给了一个可以改变经济规则的特权账户；宁可让费率变更走协议变更流程（宪法第十五条） |
| **启用 `contractNativeMinterConfig`** | 引入通胀能力即引入信任假设（谁能铸、铸多少）。若未来确需增发，应作为独立功能规格设计（权限模型 + 安全分析 + 治理），不在此顺手启用 |

## 影响

### 直接影响

- 任何持有 KARMA 支付 gas 的账户都能部署合约。链上会出现项目方无法预先审查的代码，其中必然包含低质量合约与诈骗合约——这是开放的固有代价，不是缺陷。
- **Gas 成为唯一的抗滥用机制**。无许可链上，费率参数从"性能调优参数"升级为**安全参数**：太低则刷链廉价，太高则用户被挡在门外。
- 项目方不承担"审查合约"的角色，但承担"提供防御工具"的责任（见下方待办）。

### 对后续功能产生的约束（本决策的下游要求）

| 功能 | 因本决策而必须包含的内容 |
|---|---|
| 智能合约 | 官方合约必须审计；优先用 OpenZeppelin，不自研 ERC20/权限/加密（宪法第六条）；官方合约地址需有权威公示渠道 |
| 区块浏览器 | 合约源码验证（verified contract）能力；诈骗合约标记机制 |
| 索引器 | 异常模式监控（大额授权、蜜罐特征、疑似仿冒代币） |
| 前端 / DApp | 代币白名单展示；对未验证合约的显著警告；授权额度提示 |
| 文档 | 面向用户的安全指引（如何识别诈骗、如何检查授权） |

### 尚未决定、但被本决策放大的问题

这三项不属于本 ADR 的范围，但开放模型使它们变得更重要，需要在相应功能中正式决策：

1. **Gas 与费率参数需要重新审视，且几乎没有补救机会**。当前 `minBaseFee = 25 gwei`、`gasLimit = 15,000,000` 是 Subnet-EVM 的默认值（见 ADR-0001 与协议参数文档），对开发网够用，但**未针对"开放网络的抗滥用需求"做过分析**。

   **2026-09-03 补充核实**——feeConfig 上线后的可改动性极其有限（Avalanche 官方文档）：

   | 途径 | 能否改 feeConfig |
   |---|---|
   | `upgrade.json` 网络升级 | ❌ 只能启停预编译，**不能修改创世 feeConfig** |
   | `feeManagerConfig` 预编译（地址 `0x0200…0003`） | ✅ 特权地址可运行时调用 `setFeeConfig` 改全部参数 —— 但本 ADR 已决定**不启用** |
   | 直接修改创世 | ✅ 但等于重新部署整条链 |

   两难由此产生：不启用 `feeManagerConfig` → 主网费率近乎不可变；启用 → 某地址永久掌握改变经济规则的权力（与去信任化冲突，也是本 ADR 否决它的理由）。

   **结论**：主网上线时定下的费率参数是**近乎永久的决定**。因此"上主网前完成费率安全评估"不是可选项，而是**上线前置条件**；且该评估必须同时回答"是否为可调性而接受启用 feeManagerConfig 的信任代价"。开发网阶段不必动（默认值是官方基线，且改动会作废创世哈希），但**不得在没有该评估的情况下上主网**。
2. **验证者模型的演进路径**。当前是 PoA（ADR-0004），管理员为单一地址。一条开放的公链通常需要走向去中心化的验证者集合（PoS 或多方治理的 PoA）——否则"任何人可部署合约"但"验证者由一人指定"在去信任化程度上是不对称的。
3. **代币经济学**。开放生态下的初始分配、增发策略（当前明确不可增发）、手续费处理（当前销毁）需要独立规格；开发网的 39,500,000 KARMA **不代表**主网方案（见 ADR-0003）。

## 迁移 / 可逆性

若未来确需限制部署（例如遭遇严重滥用），启用白名单是一次**协议变更**，须走宪法第十五条流程：

1. 新增规格说明为何必须限制、限制到什么程度；
2. 在 `blockchain/protocol.json` 增加对应字段并递增 `configVersion`；
3. 创世增加 `contractDeployerAllowListConfig`（含 admin / manager / enabled 三类角色）→ **创世哈希改变** → 现有链数据被 stamp 守卫拒绝；
4. 对已上线的主网，这属于硬分叉级变更，需要升级窗口与全体验证者协同——**代价远高于开发网**；
5. 补充权限管理流程与回归测试，完成安全分析后方可实施。

反之，若从许可制放开，技术上更简单，但会面临"为何当初限制"的信任成本。这也是本决策选择"先开放"的重要理由。
